# 《个人工具展示网站》需求文档审阅报告

> **状态说明**：本报告为 2026-09-20 的首轮审阅快照，记录当时两份文档的状态与问题。报告中的待确认项与待修正项**已于同日全部处理完毕**：设计决策见 `docs/doc/01-需求与范围/设计决策记录-托管范围与留言联系方式.md`，文档修订见 PRD v1.2 与一期清单 v1.2 的修订记录。阅读本报告时请以其记录的历史状态为准，不要据其判断文档现状。

**审阅基准（以你的原始表述为准）**

1. 个人网站，用于**集中展示并托管**个人开发的小工具（APP、Python 脚本等）；
2. 为**每个小工具建立独立专题页面**；
3. 访客可在**对应专题下留言**，以收集用户反馈与 BUG 报告。

**审阅方法**：以基准需求为锚点逐条比对覆盖度，并交叉核对两份文档之间的一致性。

## 一、总体结论

文档整体质量良好，基准需求的三大要素（工具展示、独立专题页、留言反馈）均有对应描述，**覆盖度约 80%**。但存在三类问题：

| 问题类别 | 数量 | 影响 |
| --- | --- | --- |
| 关键遗漏 | 6 项 | 直接影响"收集反馈与 BUG"的核心目标能否达成 |
| 模糊表述 / 需澄清 | 9 项 | 开发期易返工或过度设计 |
| 偏离原意 / 前后矛盾 | 8 项 | 两份文档口径不一致，暂不能作为开发依据 |

**最重要的一条判断**：两份文档都把"留言"当成一个**展示型功能**来写，而没有把它当成一条**反馈收集管道**来设计。

你的核心诉求是拿到"可用的 BUG 报告"，但当前留言字段被定义为 `昵称 + 内容 + 时间` 三项——缺少版本、平台、联系方式等定位问题所需的最小信息。**功能都在，但闭环不成立。** 这是本次审阅最需要修正的地方。

## 二、关键遗漏（P0：直接影响核心目标）

### P0-1　留言缺少联系方式，无法二次触达用户（最致命）

- **现状**：PRD 2.1.2 / 4.2 定义留言字段为"昵称、留言内容、提交时间"，无任何联系方式。清单第 3 节同样只有"匿名/自定义昵称留言""留言内容、时间展示、分页"。
- **问题**：在"无需注册登录"的前提下，一旦需要追问复现步骤、告知修复结果、发测试包，**你将完全无法触达该用户**。用户提交后不会主动回来刷新，反馈只能是一次性的、低信息量的。
- **修正建议**：留言表单增加**选填**的邮箱/联系方式字段，并在文档中标注可见性（"仅管理员可见，用于问题跟进，不公开"）与隐私说明。这一项的改造成本极低，但决定了反馈管道是否可用。

### P0-2　BUG 类留言缺少结构化字段

- **现状**：PRD 2.1.2 提出留言"分类场景"支持体验/建议/BUG/咨询，但**只停留在分类标签，没有配套字段**。
- **问题**：BUG 报告最常见的失效原因是"说不清版本与复现路径"。你无法判断他报的是哪一版、跑在 Windows 还是 Android。自由文本无法弥补。
- **修正建议**：停留"分类 = BUG"时动态追加必填项——① 工具版本号（可由专题页当前版本自动带出，减少用户输入）② 运行平台/系统版本 ③ 复现步骤 ④ 报错信息文本。
- **关联提醒**：清单把"留言图片上传"整体推到二期。截图是定位 BUG 最高效的手段，建议重新评估是否放入一期（若坚持不做，至少应保留字段位，避免二期改表）。

### P0-3　管理员回复没有通知闭环

- **现状**：PRD 4.1 仅写"管理员回复公开可见"；4.2 未涉及通知；清单"一期明确不做"中也未列此项。
- **问题**：反馈闭环少了一半——你回复了，用户不知道。
- **修正建议**：一期可以不做，但必须在文档中**显式标注为已知限制**并列入二期（前提是 P0-1 已落地，否则二期也无从实现）。当前状态属于"未被识别的缺口"，而非"主动放弃的取舍"。

### P0-4　内容合规与上线前置条件完全缺失（两份文档零提及）

- **现状**：无一处涉及服务器地区、域名、备案、隐私政策。
- **问题**：本站形态是"公网可访问 + 允许匿名发布内容"，这带来两项硬前置：
  1. 若使用中国大陆服务器，需 ICP 备案；而"留言/评论"类站点的备案与内容监管要求更严，你需要**先审后发或关键词拦截 + 及时清理**的机制，并有责任主体。
  2. 需公示隐私政策与免责声明（工具使用风险免责、留言信息的收集与用途说明）。
- **修正建议**：新增"上线前置与合规"章节，明确服务器归属地、备案安排、留言内容责任与应急删除流程。这一项若忽略，可能导致开发完成后无法上线。

### P0-5 "托管"的存储与成本边界未定义（同时属"偏离原意"）

- **现状**：PRD 1.2 写"支持各类工具资源在线上传、在线下载"，4.3 仅列举了文件类型。
- **问题**：
  - 未定义存储介质（服务器本地磁盘 / 对象存储）；
  - 未定义单文件大小上限与总容量；
  - 未定义下载流量与带宽方案。**APK 常见 30–200MB，若走服务器本机带宽，几次下载即可能打满，直接与 PRD 5.1"打开延迟 ≤1.5s"冲突。**
  - "托管"的语义未收敛：是指"文件存放 + 下载分发"，还是包含"脚本/服务可在线运行"？**这两种理解对应完全不同的架构。** 按你原始表述中"托管"一词，此处最需要你亲自定调。
- **修正建议**：明确写为"托管 = 文件存储与下载分发"，并给出容量、单文件上限、超限策略（建议对象存储 + CDN 直链下载，与站点主机解耦）。

### P0-6　数据模型完全缺失

- **现状**：两份文档都是功能描述，**没有任何字段清单或表结构**（工具、版本、资源文件、留言、回复、分类）。
- **问题**：从功能描述直接进入开发，字段会在实现中随机定型，后期改动成本高。
- **修正建议**：补一节"数据实体与字段"。其中两处关系必须写清：
  1. 工具 ↔ 版本文件：一对多，需明确"最新版本"如何标识、历史版本是否默认折叠；
  2. 留言 ↔ 管理员回复：一对多还是覆盖式。PRD 提到"管理员可在前台回复，形成问答交互"，**"问答交互"暗示多条回复并存，但未定义**。

## 四、偏离原意与前后矛盾（P1）

### 4.1 清单存在一处技术口径错误（建议立即修正）

> 清单开篇："轻量化、无登录用户体系、**纯静态展示+后台管理**"

**"纯静态"与文档其余要求互斥**——文件上传、留言写入、状态流转都需要服务端与数据库，纯静态站点无法实现。

**建议改写为**："前台页面静态化渲染（利于加载速度与 SEO）+ 轻量后端 API + 数据库"。

### 4.2 两份文档之间的覆盖不一致（共 4 处）

| 项目 | PRD | 清单 | 判断 |
| --- | --- | --- | --- |
| 留言分类（体验/建议/BUG/咨询） | 有（2.1.2） | **完全没有** | **清单丢了最关键的反馈分类字段，必须加回** |
| 留言状态 | 4 种（未处理/已处理/已跟进/无需处理） | 2 种（未处理/已处理） | 需统一口径 |
| "全部工具列表页" | 有（三、2） | 无 | 需统一 |
| "关于我"页面 | 有（三、4） | 无（但导航栏要求包含"关于我"） | 需统一 |

### 4.3 PRD 内部矛盾 1 处

> PRD 2.2.3 后台设置含"网站基础开关（留言功能开启/关闭、**新留言提醒**）"，但 6.2 把"新留言后台消息提醒"列入**二期**。

一期不做提醒功能，却保留提醒开关——应一并移除或明确为二期。

### 4.4 主体混淆 1 处

> PRD 1.2："支持各类工具资源**在线上传、在线下载**"

上传是**后台管理员**行为，下载是**前台访客**行为，混在一句里会误导实现。建议拆分为"后台资源上传管理""前台资源下载"。

### 4.5 一期策略未定 1 处

> 清单："不做……**评论审核复杂流程**" 　vs　PRD 5.3："留言内容**关键词过滤**"

两者不冲突，但"先发后审（关键词拦截）"与"先审后发"是不同策略，直接影响违规内容的处置成本与站点的法律风险敞口。需明确选择。

### 4.6 场景遗漏 2 处

1. **工具下架/删除后，其留言与已流出的下载链接如何处置** —— PRD 2.2.1 未涉及。是否有软删除与恢复期？
2. **前台"管理员回复"的鉴权方式未定义** —— 前台回复是否需登录态？是否复用后台账号？如何防止越权？

### 4.7 对"Python 脚本"这类工具的适配缺失

文档只提供了**一种分发形态**：上传 zip / apk → 用户下载。但脚本类工具的常见实践是：

- 提供**代码仓库外链**（GitHub / Gitee）而非打包下载；
- 纯前端小工具提供**在线试用 / 演示**（iframe 内嵌），这往往是比下载更好的分发与展示形式。

两份文档均未提及"外链型资源"或"在线体验"，这对"APP、Python 脚本等"的表述覆盖不足。

## 五、编辑级问题（P2）

1. **字段冗余**：PRD 2.1.2"开发时间 / 最新版本 / 更新时间"三者语义重叠，"开发时间"对访客价值偏低，可删。
2. **统计归属不清**：PRD 2.2.2 有"反馈统计（留言数/BUG 数/建议数）"，但 6.1 一期必做未列、6.2 二期只列"可视化面板"；清单则将统计整体划为"不做"。需明确一期是否至少做计数。
3. **交付标准不可验收**：PRD 七、"功能完整无BUG"无法作为验收依据，应替换为用例清单（见第六节）。
4. **文档元信息缺失**：两份文档均无版本号、日期、修订记录，也无"待确认问题"清单，后续迭代无法追溯。
5. **语义不明**：PRD 2.1.3 底部"更新记录"——指站点更新日志，还是工具更新日志？
6. **安全要求不可落地**：PRD 5.3"上传文件安全校验，禁止上传违规、恶意文件"是目标而非手段。可落地写法应为：扩展名白名单 + 文件重命名存储 + 存储目录禁止执行 + 单文件大小与配额限制 + 上传者鉴权。

## 六、验收标准建议（用于替换"功能完整无BUG"）

1. 后台新建一款工具并上传 2 个版本文件 → 前台 30 秒内可搜索到并进入其专题页，两个版本均可正常下载，文件大小显示正确。
2. 未登录访客在专题页提交一条"BUG"类留言 → 提交成功、前台可见、后台可检索、归属工具正确、留言计数 +1。
3. 管理员回复该留言 → 前台公开可见且位置正确。
4. 60 秒内同一来源连续提交 10 条留言 → 触发限流，给出明确提示且不产生脏数据。
5. 375px 宽手机端完成"找到工具 → 下载 → 留言"全流程，无横向滚动、无遮挡。
6. 工具下架后 → 前台列表与专题页不可访问，后台数据保留且可恢复。
7. 上传一个超限文件 / 非白名单类型文件 → 被明确拒绝并提示原因。

## 八、对"一期清单"的最小修订建议

**建议加入一期（4 项，成本低、收益高）**

1. 留言表单增加**选填联系方式**字段；
2. 增加**留言分类**（BUG / 建议 / 体验 / 咨询），并在 BUG 时追加版本与平台字段；
3. 统一两份文档的分类口径、留言状态口径、页面清单；
4. 修正"纯静态展示"这一表述。

**建议从一期移除或标注（1 项 + 1 项）**

1. 移除后台"新留言提醒"开关（功能已被划入二期）；
2. 将"回复无通知"显式标注为**已知限制**，列入二期待办。

**建议一期明确以下边界**：单文件大小上限、限流阈值、先发后审策略、下架工具的数据处置规则。
