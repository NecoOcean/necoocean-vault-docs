## 使用说明

1. **本草案已可直接用于接口评审**：§1–§4 的契约层不依赖任何未定参数，可直接确认。
2. **标记含义**：
   - ✅ = 已决策（2026-09-21 的 Q-1 ~ Q-4）
   - ⚠️ = 参数待确认，已给建议值，按建议值可先实现
   - 🔒 = 该接口涉及敏感字段或安全约束，须逐条落实输出白名单
   - 🆕 = v0.2 新增内容
   - 🔀 = 分期实现项（一期简化版 / 二期完整版）
3. **🔀 审核策略的分期落地（本章最重要的一节）**

   终态（Q-2 决策）：**先审后发**。但一期先上线**先发后审**，二期再切换。**接口层必须按终态形状设计**，否则二期切换时要同时改接口、改前端、改数据库——那是典型的返工。

   **实现机制：单一开关 + 默认值**

   | 层 | 一期行为 | 二期行为 | 切换成本 |
   |---|---|---|---|
   | 数据库 | `messages.audit_status` 字段**建好**，新留言默认写入 `2`（已通过） | 默认值改为 `1`（待审核） | 改一个默认值 |
   | 提交接口 C-07 | 按当前策略自动置 `audit_status`，返回真实状态 | 同左（逻辑不变） | 无需改动 |
   | 留言列表 C-06 | 查询条件 `audit_status = 2` | 同左（**逻辑不变**） | 无需改动 |
   | 审核接口 C-45 ~ C-47 | **实现**，但后台无待审数据可操作 | 投入使用 | 无需改动 |
   | 后台列表 C-34 | 支持 `audit_status` 筛选，默认视图不筛 | 默认视图改为 `audit_status = 1` | 改一个默认值 |
   | 前台文案 | 不展示"审核通过后公开显示" | 按 §4.2 新增文案展示 | 改一处文案 |
   | 索引 | `messages(audit_status, created_at)` **直接建** | 无需新增 | 无 |

   **这样设计的三点理由**：
   1. **C-06 的查询条件在两种策略下完全相同**（都是"只看已通过"）——先发后审时所有留言的 `audit_status` 就是 `2`，语义自洽，不需要写分支判断。这是整个预留方案能成立的关键。
   2. **C-45 ~ C-47 一期实现但不产生数据**，成本仅是几个接口的空转，却避免了二期补做接口与回归测试前端。
   3. **前台文案切换是唯一需要在二期改动的前端资产**，且它天然属于文案层，改动风险最低。

   > ⚠️ **一期不得省略 `audit_status` 字段**。若为"简化"把该字段延到二期再加，则二期需要：改表 + 数据回填 + 改 C-06 查询条件 + 改 C-07 返回结构 + 新增审核接口 + 回归全部留言相关用例。**这是本方案唯一必须守住的底线。**

4. **与 PRD 待补项的对应关系**（本草案解决其中 4 项）：
   - PRD §6.1 漏列的 7 项功能（分类管理、存储占用、留言置顶、反馈统计、网站基础设置、外链资源维护、数据导出）→ 本草案已全部纳入接口清单，**同时须回填 PRD §6.1**
   - PRD §8 缺 `site_settings` 实体 → 见 §5.3
   - PRD §8 缺审核状态与关键词标记字段 → 见 §5.1

## 一、统一约定（Contract）

### 1.1 路由规范

| 项 | 约定 |
|---|---|
| API 前缀 | `/api/v1`（前台与后台共用前缀，用路径段区分） |
| 公开接口 | `/api/v1/public/*` —— 无需鉴权，可被匿名访问 |
| 后台接口 | `/api/v1/admin/*` —— 全部需登录态，路由不出现在任何前台页面 |
| 下载接口 | `/download/{file_id}` —— **不带 `/api` 前缀**，因需被浏览器直接导航（`<a href>`）而非 XHR 调用 |
| 管理后台页面入口 | ⚠️ 建议随机化路径（如 `/manage-{8位随机串}/`），在环境变量中配置，不在代码仓库硬编码 |
| 专题页 URL | `/{slug}` —— 一级路径，slug 仅英文/数字/连字符，创建后不可变 |
| 路径风格 | 资源名用复数、小写、连字符（`/api/v1/public/tools`、`/api/v1/admin/release-notes`） |
| 结尾斜杠 | 统一不加 |

> **为什么下载接口不带 `/api` 前缀**：它返回 302 而非 JSON，语义上不属于 API；且需让访客直接点击下载，不带前缀更利于 CDN 与缓存策略区分。

### 1.2 鉴权方案

> 🔀 **前后端分离补充约定（2026-09-21）**：架构已定为**严格前后端分离**（前端 Vue 3 独立项目，后端仅输出 JSON）。以下鉴权方案在此基础上确定，并新增同源部署与前端配合要求，详见 §1.8。

| 项 | 约定 |
|---|---|
| 方式 | ✅ **Cookie-based Session**（定稿）——单管理员 + 同源部署下复杂度最低：浏览器自动管理，前端无需处理存储/刷新/过期 |
| Cookie 属性 | `HttpOnly` + `Secure` + `SameSite=Lax`；`Path=/` |
| 会话有效期 | ⚠️ 建议 **12 小时**（个人站，兼顾安全与免重复登录）；无滑动续期 |
| CSRF 防护 | 采用 **双提交 Cookie**：登录成功后下发非 HttpOnly 的 `csrf_token` cookie，所有写操作（POST/PUT/PATCH/DELETE）须在请求头 `X-CSRF-Token` 中回传同值，服务端比对 |
| CSRF 例外 | 公开写接口（留言提交）**豁免 CSRF**（无登录态，无越权前提），但受 §1.6 限流约束 |
| 未登录响应 | HTTP **401**，错误体 `code = 40100` |
| 无权限响应 | HTTP **403**，错误体 `code = 40300` |
| 登录失败锁定 | 连续失败 ⚠️ **5 次**（建议值）后锁定 ⚠️ **15 分钟**（建议值）；`admin_users.failed_attempts` 计数，登录成功清零 |

### 1.3 统一响应结构

所有 `/api/v1/*` 接口统一信封；`/download/{file_id}` 除外（返回 302）。

**成功**
```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

**失败**
```json
{
  "code": 42201,
  "message": "邮箱格式不正确，可留空。",
  "data": null
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | int | 0 表示成功；非 0 为业务错误码，见 §4 |
| `message` | string | 可直接展示给用户的文案（公开接口）；后台接口可返回更详细的技术描述 |
| `data` | object / array / null | 业务数据；失败时为 `null` |

> **设计要点**：`message` 面向用户、`code` 面向代码。前端按 `code` 分支处理，按 `message` 兜底展示——这样文案调整不会破坏前端逻辑（PRD §4.2 的"标准文案"即依赖此约定）。

### 1.4 分页约定

**请求参数**（所有列表接口统一）

| 参数 | 类型 | 默认 | 上限 | 说明 |
|---|---|---|---|---|
| `page` | int | 1 | —— | 页码，从 1 开始 |
| `page_size` | int | 20 | ⚠️ 100（建议） | 每页条数 |

**响应结构**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "list": [],
    "pagination": {
      "page": 1,
      "page_size": 20,
      "total": 137,
      "total_pages": 7
    }
  }
}
```

> 采用**页码分页**而非游标分页：留言总量级为百级，页码分页便于"跳到第 N 页"，实现与调试成本更低。

### 1.5 数据类型与格式约定

| 类型 | 约定 | 说明 |
|---|---|---|
| 字段命名 | `snake_case` | 与 PRD §8 数据模型一致，避免前后端两套命名 |
| 时间 | `ISO 8601`，带时区偏移：`2026-09-21T09:57:52+08:00` | 服务端一律存 UTC+8；前端按浏览器时区展示 |
| 布尔 | `true` / `false` | 数据库 `tinyint(1)` → 接口层转布尔，**不返回 0/1** |
| 枚举 | 返回**数值** + **文本**双字段 | 如 `category: 3, category_text: "BUG报错"`；文本由后端提供，前端不硬编码中文映射（避免枚举文案改动时前端不同步） |
| 空值 | `null`，不使用空字符串代替 | 前端据此区分"未填写"与"填了空" |
| ID | `int` | 不使用雪花 ID；个人站量级无需分布式 ID |
| 金额 | 不涉及 | —— |
| 多选字段 | ⚠️ 建议 **字符串数组**，如 `platforms: ["Windows", "Android"]` | 数据库用逗号分隔存储，接口层转换。**此为 PRD §8.1 未定项，需确认** |
| 大整数 | 文件大小用 `int`（字节），前端负责格式化 | 200 MB = 209715200，在 int 范围内 |

### 1.6 限流与防滥用 ⚠️

| 场景 | 粒度 | 阈值（建议） | 超限响应 |
|---|---|---|---|
| 留言提交 | `ip_hash` | **5 条 / 60 秒** | HTTP 429，`code = 42901`，文案：`提交过于频繁，请稍后再试。` |
| 留言提交（单工具） | `ip_hash` + `tool_id` | 3 条 / 60 秒 | 同上 |
| 后台登录 | `ip_hash` | 5 次失败 / 15 分钟 | HTTP 429，`code = 42902`，文案：`登录失败次数过多，请 15 分钟后再试。` |
| 公开读接口 | —— | 不单独限流 | 页面资源由源站/COS 托管、接口响应体仅数 KB，一期日活约 100 人无需限流；**若出现刷量再按 `ip_hash` 补限流规则** |

> **阈值确立依据**：《验收用例集》B-14 用例为"60 秒内连续提交 10 条留言触发限流"，故生产阈值必须严格小于 10。建议取 **5 条/60 秒**（留出正常用户连续提问的余量，同时满足 B-14）。

> `ip_hash` 为 `sha256(ip + 服务端盐)`，**不存储明文 IP**（PRD §8.5、§4.2）。

> ⚠️ **真实 IP 获取（部署后必查项）**：生产环境应用位于 Nginx 之后，`getRemoteAddr()` 只会拿到 `127.0.0.1`。若不做处理，**全站请求会被当作同一 IP，限流将误伤所有访客**。必须：① Nginx 配置 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`；② 应用侧（Spring Boot）启用 `server.forward-headers-strategy=native`；③ 取 `X-Forwarded-For` **第一段** 作为客户端 IP，再做 `sha256` 得到 `ip_hash`。该字段缺失或为内网地址时，应降级为"取不到则不限流"而非"归入同一桶"，避免误伤。

### 1.7 缓存约定

| 接口类别 | 缓存策略 |
|---|---|
| 公开列表 / 详情 | `Cache-Control: public, max-age=60`（前端可在此基础上做内存缓存，避免 30 秒轮询之外的高频重复请求） |
| 留言列表 | **不缓存**（`no-store`），因审核后状态变化需即时反映 |
| 下载 302 | **不缓存**（`no-store`），因签名地址带时效 |
| 后台接口 | `no-store` |
| 前端构建产物 | 由 Nginx 按内容指纹设置长缓存（`immutable`），**不属于本节接口缓存范畴** |

### 1.8 前后端分离协作约定 🔀（2026-09-21 新增）

架构已定为**严格前后端分离**：前端独立项目（Vue 3 + Vite）负责全部页面与交互，后端**仅通过 HTTP API 返回 JSON**，不输出任何 HTML。以下为接口层必须遵守的协作规则，其余架构内容见《前后端分离架构说明》v1.2。

| 项 | 约定 |
|---|---|
| **部署形态** | **同源部署**：前端与 API 同一域名（前端 `/`、API `/api/v1/`），**故不启用 CORS**：后端不返回 `Access-Control-*` 头，也不处理 OPTIONS 预检 |
| 跨域变更时 | 若前端迁至独立域名（演进阶段 1：前端产物迁 COS 静态托管），后端须增加 CORS 白名单（仅该域名）+ `Allow-Credentials: true`，且 Cookie 的 `SameSite` 须改为 `None; Secure` |
| **前端请求** | 一律 `credentials: 'include'` 以携带会话 Cookie；**前端不读取、不存储会话标识** |
| **CSRF 前端配合** | 前端从 `csrf_token` Cookie 读值，写入请求头 `X-CSRF-Token`（仅写请求）；公开写接口豁免 |
| **登录态判断** | 前端不自行判断，以接口返回 `40100` 为准并跳转登录页 |
| **错误呈现** | 前端按 `code` 映射用户文案；`message` 面向用户、可直接展示 |
| **上传流程** | 前端：`C-28 取预签名凭证` → `直传 COS` → `C-29 complete`（回传对象键 + SHA-256）。文件不经后端、不经源站 |
| **下载** | 前端跳转 `/download/{file_id}`（非 XHR），后端 302 至 COS 预签名地址 |
| **封面图** | 前端直连 COS `covers/` 公开前缀 URL，**不经源站**（3 Mbps 带宽约束下必须） |
| **实时性** | 留言刷新：前端轮询 C-06，固定 30 秒；一期不引入 WebSocket |
| **后端禁止项** | 后端不得包含任何模板文件或 HTML 输出；除 `/download/{file_id}` 的 302 外，所有响应 `Content-Type` 必须为 `application/json` |

### C-04b　查询留言提交状态 🔒 🔀

| 项 | 内容 |
|---|---|
| 方法 / 路径 | `GET /api/v1/public/messages/{id}/status` |
| 用途 | **为二期「先审后发」预留的状态查询接口**。一期（先发后审）留言即时公开，本接口价值低 |
| 鉴权 | 无 |
| 安全设计 | ⚠️ **本接口只接受留言 `id`，返回体仅含状态字段**。理由：留言 id 为自增整数、可被枚举——若返回留言内容或邮箱，等于留下数据泄露通道。**只返回状态，不返回内容** |
| 🔀 一期处理 | **实现但不前台调用**（成本极低）；或延至二期随审核接口一并交付 |
| 缓存 | `no-store` |

**响应 `data`**
```json
{
  "id": 9001,
  "audit_status": 2,
  "audit_status_text": "已通过",
  "created_at": "2026-09-20T16:00:00+08:00"
}
```

| `audit_status` | 文本 | 前台留言区是否可见 |
|---|---|---|
| 1 | 待审核 | 不可见（**二期才可能出现此值**） |
| 2 | 已通过 | 可见（**一期恒为此值**） |
| 3 | 未通过 | 不可见（且不在前台提示原因，避免暴露审核规则） |

> ⚠️ **本接口的实际可用性存疑**（见 §6.2 Q-14）：用户提交后若离开页面，不会留存留言 `id`，也就无从查询。**建议一期不做前台入口**，二期状态告知优先由邮件通知承担。本接口保留的价值是"预留形状"。

### C-07　提交留言

| 项 | 内容 |
|---|---|
| 方法 / 路径 | `POST /api/v1/public/tools/{slug}/messages` |
| 用途 | 提交反馈（PRD §2.1.2、§4.2） |
| 鉴权 | 无（免登录） |
| CSRF | **豁免**（无登录态） |
| 限流 | §1.6：`ip_hash` 5 条 / 60 秒 |
| 幂等性 | ⚠️ 建议不做幂等键；由限流防止重复提交（个人站无需复杂幂等设计） |

**请求体**
```json
{
  "nickname": "匿名",
  "category": 3,
  "content": "点击下载按钮无响应……",
  "contact_email": "user@example.com",
  "os_platform": "Windows 11",
  "tool_version": "1.2.0",
  "repro_steps": "1. 打开专题页\n2. 点击下载"
}
```

| 字段 | 必填 | 类型 | 约束 | 校验失败 `code` |
|---|---|---|---|---|
| `nickname` | 是 | string | 1–50 字符；默认 `匿名` | 42202 |
| `category` | 是 | int | 枚举 1/2/3/4（见 §5.1） | 42203 |
| `content` | 是 | string | 1–⚠️ **2000** 字符（建议） | 42204 |
| `contact_email` | 否 | string | ≤254 字符；格式校验；留空传 `null` 或不传 | 42201 |
| `os_platform` | 条件 | string | 仅 `category = 3` 时可传，≤50 字符 | 42205 |
| `tool_version` | 条件 | string | 仅 `category = 3` 时可传，≤32 字符 | 42205 |
| `repro_steps` | 条件 | string | 仅 `category = 3` 时可传，≤⚠️ **1000** 字符（建议） | 42205 |

> **"条件"的含义**：非 BUG 类留言若传入这三个字段，服务端**忽略并置 `null`**（不报错，避免前端切换分类时残留值导致提交失败）；BUG 类留言这三个字段均为**选填**（PRD 明确标注"选填"）。

**归档行为（🔀 分期实现）**

接口按**终态形状**定义，通过一个配置项切换行为。**接口形状在两种策略下完全一致**。

| 项 | 内容 |
|---|---|
| 落库规则 | 服务端根据审核策略配置决定 `audit_status` 取值：<br>**一期（先发后审）**：置 `2`（已通过），留言即时公开<br>**二期（先审后发）**：置 `1`（待审核），进入审核队列 |
| 关键词检测 | 两种策略下**都执行**：命中则 `keyword_flagged = 1`，供管理员优先查看 |
| 一期关键词的作用 | 仅"标记 + 后台可筛"，**不做拦截、不做不公开**（与《待确认参数台账》A-5 口径一致） |
| 二期关键词的作用 | 仍是"标记优先复核"，**不做自动拦截**——终态是先审后发，所有留言都要过人工，关键词只影响队列顺序 |
| 响应差异 | 仅 `audit_status` 字段的返回值不同（一期恒为 `2`），**字段结构完全一致** |

> **为什么一期不写分支判断**：`audit_status` 的赋值由服务端在落库时完成，C-06 的查询条件恒为 `audit_status = 2`。一期时这个条件对所有留言都成立，逻辑自然运行，无需 if/else。二期只需把落库默认值从 `2` 改成 `1`。

**成功响应 `data`**
```json
{
  "id": 9001,
  "audit_status": 2,
  "audit_status_text": "已通过",
  "keyword_flagged": false,
  "created_at": "2026-09-20T16:00:00+08:00"
}
```

> **前端不再返回留言完整内容**（🔀 两种策略下均如此设计）。原因：接口形状必须对两种策略都成立——先审后发时留言尚未公开，返回完整对象会让前端误以为可以"即时插入当前页面"；先发后审时虽已公开，但前端保持同一套处理逻辑可避免二期改动。
>
> 前端统一处理：提交成功后**重新拉取 C-06 列表**（一期即可看到自己的留言；二期则需等审核），并展示对应提示文案。
>
> | 策略 | 前端提示文案 |
> |---|---|
> | 一期（先发后审） | 沿用现有文案，或不提示（留言已即时出现在列表） |
> | 二期（先审后发） | **`留言已提交，管理员审核通过后公开显示。`**（新增标准文案，须与前台表单、隐私政策页一致，ADR-002 §2.2） |
>
> 若审核未通过，留言不出现在前台，且**不向用户展示未通过原因**（避免暴露审核规则、降低绕过成本）。

### 3.5 资源文件管理

> **上传为两阶段流程**（ADR-001 §3.2、PRD §4.3）。ADR-001 目前写作"先落库占位 **或** 写入后登记"二选一，本草案**定稿为明确的两阶段**（原因见下方说明）。

**阶段一：签发上传凭证**

| 编号 | 方法 / 路径 | 用途 |
|---|---|---|
| C-28 | `POST /api/v1/admin/tools/{id}/files/upload-ticket` | 申请预签名上传凭证 |

**请求体**
```json
{
  "display_name": "示例工具-v1.2.0.zip",
  "ext": "zip",
  "file_size": 104857600,
  "version": "1.2.0",
  "platform": "Windows"
}
```

**服务端校验**（在签发前完成，避免用户上传完才被拒）
1. `ext` 在白名单内（见 PRD §4.3，**允许 19 类**，2026-09-21 追加 `.whl` / `.AppImage` / `.deb`）→ 否则 `code = 42206`（`文件类型不允许上传。`）
2. `file_size` ≤ 200 MB → 否则 `code = 42207`（`文件大小超过 200 MB 上限。`）
3. `version` 非空、`(tool_id, version)` 组合合法
4. 生成 `object_key = {tool_id}/{version}/{uuid}.{ext}`（**不使用原始文件名**，ADR-001 §3.1）

**响应 `data`**
```json
{
  "file_id": 501,
  "object_key": "1/1.2.0/7f3a9c2e-....zip",
  "upload_url": "https://<bucket>.<endpoint>/...&X-Amz-Signature=...",
  "upload_method": "PUT",
  "upload_headers": { "Content-Type": "application/octet-stream" },
  "expires_at": "2026-09-21T10:57:52+08:00"
}
```

> ⚠️ **上传签名有效期未定**（下载侧已定 5 分钟）。须覆盖 200 MB 上传耗时，**建议 30–60 分钟**。

**阶段二：完成登记**

| 编号 | 方法 / 路径 | 用途 |
|---|---|---|
| C-29 | `POST /api/v1/admin/files/{file_id}/complete` | 前端直传完成后登记落库 |

**请求体**
```json
{
  "sha256": "a3f1...（64位小写）",
  "file_size": 104857600
}
```

**服务端动作**：核对 `object_key` 对应对象是否存在 → 落库 `sha256` / `file_size` / `created_at` → 按需调整 `is_latest`（见 §5.3）

> ⚠️ **须定稿：SHA-256 核验方式**。ADR-001 §3.2 要求"由后端核验"，但后端若自行计算需回拉 200 MB 对象，与"避免经过应用服务器"的设计目标**直接冲突**。

> ✅ **Q-3 决策：采用方案 A —— 信任前端回传的 `sha256`，服务端仅校验格式（64 位小写十六进制）**。
>
> 依据：单管理员场景下不存在第三方上传者，无篡改动机；校验值的用途是"供下载者核对文件完整性"，而非服务端安全边界。同时保留了"避免 200 MB 对象回拉应用服务器"的设计收益。
>
> **方案 A 的已知局限（须在验收与运维中体现）**：
> 1. 若前端计算有 bug 或用户在传输中丢包，落库的校验值可能与实际文件不符——**前台展示的校验值将失去意义**。
> 2. **缓解措施**：下载区已在 PRD §4.3 公示"文件由作者本人打包上传，下载后请自行核对校验值"。建议在管理员上传流程中增加一步**本地自行核对**（上传后下载一次、与本地哈希比对），成本约 1 分钟，可完全消除该风险。
> 3. **不得**改用对象存储 ETag 替代 SHA-256——分片上传的 ETag 不是 MD5，与 SHA-256 语义不同，直接展示会在用户核对时产生误导。

> PRD §8 已定义 7 个实体。以下 5 项是本草案在定义接口过程中发现的缺口，**须补入 PRD §8 后方可实现**。

### 5.0 枚举值全集（须写入 PRD §8.5）

**`messages.category`**（PRD §8.5 已定义，此处补全文本映射）
| 值 | 文本 |
|---|---|
| 1 | 使用体验 |
| 2 | 功能建议 |
| 3 | BUG报错 |
| 4 | 问题咨询 |

**`messages.status`**（PRD §8.5 已定义；⚠️ "已处理"与"已跟进"语义边界不清，须补定义）
| 值 | 文本 | 建议定义 |
|---|---|---|
| 1 | 未处理 | 尚未查看或尚未回复 |
| 2 | 已处理 | **已回复且问题已解决** |
| 3 | 已跟进 | **已回复但需等待用户反馈或后续版本** |
| 4 | 无需处理 | 广告 / 无效 / 重复 / 不采纳 |

### 5.1 新增字段：留言审核状态与关键词标记（🔀 分期实现的核心）

**为什么需要**：终态（先审后发）要求留言有明确的"是否已公开"状态，而 PRD §8.5 的 `status`（未处理/已处理/已跟进/无需处理）是**管理员内部处理进度**，不能兼作审核状态——二者语义与生命周期都不同（审核在前、处理在后）。

**须补入 `messages` 表：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `audit_status` | tinyint, **default 2（一期）** | **1=待审核，2=已通过（公开可见），3=未通过（不公开）**<br>🔀 **一期默认 `2`**（先发后审，留言即时公开）；**二期改为 `1`**（先审后发） |
| `keyword_flagged` | tinyint, default 0 | 0=未命中，1=命中关键词（仅用于排序与醒目提示，不做自动处置／拦截） |
| `audited_at` | datetime, NULL | 审核时间。一期有值的情况：管理员主动标记过；二期为审核动作时间 |

**索引须同步补充（一期即建）**：`messages(audit_status, created_at)`

> **索引一期就必须建的第 3 个理由**：除"避免二期改表"外，一期建好后 `audit_status` 恒为 `2`，该索引的区分度虽低，但**可在二期切换时立即生效、无需 DDL 变更窗口**。考虑到留言数据会累积，二期再补索引需要在线加索引（或短暂锁表），对本项目属可避免的运维动作。

> **两套状态的职责边界（不可合并）**：
> | 状态字段 | 管什么 | 取值 |
> |---|---|---|
> | `audit_status` | **是否公开** | 待审核 / 已通过 / 未通过 |
> | `status` | **管理员内部处理进度** | 未处理 / 已处理 / 已跟进 / 无需处理 |
>
> 审核通过后 `status` 仍可为"未处理"——把两者合并会导致"已公开但未处理"这一正常状态无法表达。

> 🔀 **分期切换对需求文档的影响（v0.3 修订）**：**一期不改动需求侧的审核口径**。PRD §9.3、《待确认参数台账》A-5 保留"先发后审"表述——因为一期实际行为确实是先发后审。**需求侧本次只需补入"预留"说明**（见 §8 第 5 项）。

> **二期切换时须改动的位置**（届时再做，本次不执行，此处仅登记备查）：
> - PRD §9.3 的"留言提交后即时公开"→"留言提交后进入待审队列，管理员审核通过后公开"
> - PRD §2.1.2 的"留言提交成功后即时插入当前页面"须改写（见 C-07 说明）

### 5.2 跨表一致性规则 ⚠️

**规则一：`tools.latest_version` 与 `resource_files.is_latest` 的同步**

| 约定 | 内容 |
|---|---|
| 唯一性 | 同工具内 `is_latest = true` 至多一条（PRD §8.4 已述） |
| 变更方式 | 通过 C-31 显式指定。服务端**在单个事务内**先将该工具所有 `is_latest` 置 0，再将目标置 1，避免中途出现 0 条或 2 条 |
| 冗余字段同步 | C-31 执行时同步将 `tools.latest_version` 更新为该文件的 `version` |
| 新增文件时 | **默认不自动成为推荐版本**，须管理员显式指定（避免误上传的旧版本覆盖推荐标识） |
| 删除推荐版本文件时 | ⚠️ **行为未定义**：建议自动将同工具内 `created_at` 最新的文件设为推荐；若无文件则 `latest_version` 置 `null` |

**规则二：`tools.platforms` 的存储与传输形态**

| 层 | 形态 |
|---|---|
| 数据库 | CSV 字符串（`Windows,Android`），PRD §8.1 的 `varchar(100)` |
| 接口 | **字符串数组** `["Windows", "Android"]` |
| 转换责任 | 服务端序列化层负责双向转换；前端只见数组 |

> 此项决定前端解析代码形态，**必须在接口定义评审时确认**。

### 5.3 新增实体：`site_settings` ⚠️

**为什么需要**：PRD §2.2.3 要求后台可配置网站标题、首页简介、版权信息、留言开关，但 §8 的 7 个实体中无对应表——**这些配置当前没有数据落点**。

| 字段 | 类型 | 说明 |
|---|---|---|
| `key` | varchar(50), PK | 配置键 |
| `value` | text | 配置值 |
| `updated_at` | datetime | 更新时间 |

**初始配置键**：`site_title`、`home_intro`、`copyright`、`about_content`、`icp_number`、`message_enabled`、`message_poll_interval`

> **为何用 KV 结构而非固定列**：配置项会随版本增加，KV 结构新增配置无需改表与迁移脚本，更契合个人项目的迭代节奏。

### 5.4 分类自定义的连带影响（Q-4 决策后）

Q-4 确认"分类开放自定义，预置 4 类"。此举解决 PRD §2.2.1 与 A-6 的冲突（**A-6 取值须改为"后台可自由增删改，预置 4 类"**），但连带以下 5 项须一并确定：

| # | 影响项 | 须确定的内容 |
|---|---|---|
| 1 | 分类删除策略 | 分类下仍有工具时：拒绝删除 / 迁移至"其他工具"（见 C-23，建议 A 方案拒绝删除） |
| 2 | 预置分类保护 | "其他工具"建议设为系统预置、不可删除（兜底与默认值依赖它） |
| 3 | 唯一性约束 | `tool_categories(name)` 建议加唯一索引，避免出现两个同名分类 |
| 4 | 排序维护 | 新增分类的 `sort_order` 取值规则；是否提供拖拽排序（建议一期仅数字输入） |
| 5 | 分类与"其他工具"的关系 | "其他工具"是普通分类还是特殊兜底分类——建议按普通分类处理，但禁止删除 |

> **成本提示**：分类自定义使 C-20 ~ C-23 四个接口成为必需，比"固定 4 类"方案多出约 2 个接口与一套分类管理页面。对个人站而言，若长期只有 4 类工具，此功能可能闲置。**但它带来的收益是"新工具类型不需要改代码/改库"**，属合理投资。

### 5.5 封面图规则补充 ⚠️

**问题**：PRD §2.2.1 要求"上传封面图"、§8.1 有 `cover_path`，但：
1. §4.3 的类型白名单（16 项）**不含任何图片格式**——封面图当前无法上传
2. 封面图命名与 §8.4 的 `object_key` 约定不一致
3. 封面图是**公开展示**的图片，而对象存储桶为**私有读写**——公开访问路径未定义

**建议补充**：

| 项 | 约定 |
|---|---|
| 允许类型 | `.jpg` `.jpeg` `.png` `.webp` |
| 单文件上限 | 2 MB |
| 存储键名 | `covers/{tool_id}/{uuid}.{ext}`（与文件区隔，便于设不同的生命周期策略） |
| 公开访问 | 建议将 `covers/` 前缀配置为**公开读**，或经独立 CDN 域名公开；**不得**将整个桶设为公开读（会破坏 ADR-001 §3.1 的私有桶约束） |
| 字段名 | 建议将 `cover_path` 更名为 `cover_object_key`，与 §8.4 命名一致 |
| 留空处理 | 未上传封面图时返回默认占位图 URL |
