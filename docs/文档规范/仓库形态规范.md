# 仓库形态规范（三仓库 + 本地工作区）

**版本**：v1.2
**生效日期**：2026-09-21
**决策人**：NecoOcean
**适用范围**：**一切采用前后端分离架构的个人项目**（不限于 `necoocean-vault`）
**上位规范**：`文档撰写通用规范.md`（本文不重复其内容，仅规定仓库形态这一专有命题）
**规范级别**：**强制**——新项目不得自行选择其他仓库形态；偏离须先修订本文

---

## 一、结论先行

**任何前后端分离项目，一律采用「三仓库 + 一个不受版本控制的本地工作区」形态。**

| # | 仓库 | 内容 | 版本节奏 |
|---|---|---|---|
| ① | 后端 | `necoocean-<项目>-backend/` | 应用版本（如 `0.1.0-SNAPSHOT`） |
| ② | 前端 | `necoocean-<项目>-frontend/` | 应用版本 |
| ③ | 文档 | `necoocean-<项目>-docs/`，其内 `docs/` 下含 `doc/` + `design/` + `文档规范/` 三个子目录（本仓库的实际路径为 `docs/doc/`、`docs/design/`、`docs/文档规范/`） | 文档版本（如 PRD v1.8） |
| — | **本地工作区** | 根目录本身 | **不纳入版本控制** |

**核心判据**：**一个仓库 = 一个部署单元 = 一条独立的版本演进线**。三者变更节奏不同，合在一处会导致版本号被动跳动。

**实证依据**：本仓库 PRD 曾因参数持续回填，版本号从 v1.1 连推至 v1.7 —— 那是"两类更新节奏不同的内容共用一个版本号"的代价。仓库形态若犯同样错误，代价会被放大到发布与回滚层面。

## 二、为什么是这一形态（决策依据）

### 2.1 三条硬理由

| # | 理由 | 说明 |
|---|---|---|
| 1 | **版本必须能独立演进** | 后端打 tag `v0.3.0` 时，前端与文档**不应**被迫跟着走。合仓后 git tag 是仓库级而非目录级的，无法单独标注 |
| 2 | **部署单元本就分离** | 后端产出 jar → 服务器；前端产出静态文件 → COS。发布流程、回滚方式、部署目标全部不同 |
| 3 | **变更需要独立历史** | "查后端某接口哪次改的"与"查 PRD 某参数哪次定的"是两个独立问题，合仓会让 `git log` 混入无关噪声 |

### 2.2 为什么不做 Monorepo

Monorepo 的收益前提是**模块间有大量代码共享、需要原子提交跨模块改动**。

**前后端分离项目的共享物只有一份 HTTP 契约**，且契约的载体是文档（接口清单），不是代码。共享前提不成立，引入 monorepo 工具链（路径过滤 CI、目录级版本模拟）的复杂度全部白付。

> **判定规则**：若某项目的前后端**确实共享代码**（如共用 TypeScript 类型定义包、共用构建工具链），则**不适用本规范**，须单独论证并记录偏离理由。这类项目在 NecoOcean 的个人项目中尚未出现。

### 2.3 为什么不用 git submodule 挂根目录

submodule 的价值是"用一个入口锁定多仓库的特定版本组合"。

| 代价 | 说明 |
|---|---|
| 克隆后子目录为空 | 必须 `git submodule update --init --recursive`，否则不知道代码为何缺失 |
| 每次改动要两次提交 | 先在子仓库提交，再回父仓库更新指针 |
| 漏更新指针即静默错版 | 父仓库指向旧 commit，协作时极难排查 |
| 分支与回滚别扭 | 需同时操作父子两层 |

对**单人开发、零代码共享**的项目，submodule **收益为零、成本为正**。**明令不采用。**

## 三、目录形态（标准）

```
<项目名>/                          ← 本地工作区，本身不是 git 仓库
├── <项目名>-backend/              ← 仓库①（独立 .git）
│   ├── .git/  → github.com/NecoOcean/<项目名>-backend
│   ├── .gitignore
│   └── src/ ...
├── <项目名>-frontend/             ← 仓库②（独立 .git）
│   ├── .git/  → github.com/NecoOcean/<项目名>-frontend
│   └── ...
└── <项目名>-docs/                 ← 仓库③（独立 .git）
    ├── .git/  → github.com/NecoOcean/<项目名>-docs
    ├── .gitignore
    └── docs/                      ← 仓库内文档根
        ├── doc/                   ← 需求、设计、接口类文档
        ├── design/                ← UI 设计交付物
        └── 文档规范/              ← 撰写与图表规范
```

> **文档仓库目录名说明**：本仓库（`necoocean-vault`）是既有项目，其仓库目录名沿用历史命名 `necoocean-vault`，**未**改名为 `necoocean-vault-docs`——改名会使已有的本地克隆与 remote 失效，成本高于收益。**新项目须使用 R4 规定的 `<项目名>-docs` 命名**。
>
> **本仓库采用布局 A**：文档仓库根下含 `docs/` 中间层，三子目录位于 `docs/doc/`、`docs/design/`、`docs/文档规范/`（2026-09-21 自布局 B 迁入）。

### 3.1 文档仓库的两种可行布局

下表描述**文档仓库内部**的三个子目录位于何处，与仓库根名无关。

| 布局 | 做法 | 适用 |
|---|---|---|
| **A：`docs/` 中间层** | 三子目录置于仓库根下的 `docs/` 内：`docs/doc/`、`docs/design/`、`docs/文档规范/` | **本仓库与新建项目均采用**；仓库根可同时容纳项目级文件（`README.md`、`CHANGELOG.md`）而结构不混 |
| **B：根目录直接承载** | 三子目录直接位于仓库根下：`doc/`、`design/`、`文档规范/` | 适合子目录全部为文档、无其他项目级文件且不打算新增的仓库 |

> **A 与 B 均为合规布局**，本规范不作强制排序；**新建项目一律采用 A**。选择依据：「仓库根是否还需容纳非文档类项目文件」与「是否接受文档内路径引用多一层前缀」。
>
> **布局可迁移，但迁移有代价**：将 B 迁为 A 或在两者间切换，须同步改写文档内全部路径引用（本仓库 2026-09-21 实测 **14 个文件、78 处**）。因此**布局一旦定下，除非有明确收益，不轻易变更**；变更须在 CHANGELOG 记录并完成全量引用校验。

### 3.2 工作区根目录应放什么

不放任何交付物。可放一个**不纳入版本控制**的说明文件（如 `README.md`），内容仅一行：

```markdown
本目录是本地工作区。三个子目录各有独立的 Git 仓库，不构成单一仓库。
后端：<项目名>-backend   前端：<项目名>-frontend   文档：<项目名>-docs
```

## 四、约束条件（强制条款）

### R1 根目录不得初始化 git

工作区根目录**不得**存在 `.git`。若已存在，须移除（保留原仓库历史则用 `git clone` 重建到子目录）。

**理由**：根目录作为仓库会吞掉子目录中的仓库（git 遇到子目录 `.git` 时默认不递归跟踪其内容，只会记成一个无法展开的 gitlink）——表现为"根仓库里看不到任何后端文件"，且两个仓库互不知晓。

### R2 子仓库不得互相嵌套

三个仓库**平级**，不存在包含关系。**禁止**把文档仓库放进 `<项目名>-backend/`（或 `-frontend/`）内，或反之。

> 📌 **不冲突提示（本仓库易误读之处）**：文档仓库**内部**的 `docs/` 中间层（布局 A）位于**文档仓库自身根下**，属仓库内目录结构，**不构成**两个仓库的嵌套——嵌套指的是仓库①/②/③ 之间的关系。判定方法：若 `docs/` 所在目录存在 `.git`，则该 `docs/` 属文档仓库内部结构，合规。

### R3 文档仓库根须有 `.gitignore`，排除两个代码仓库

文档仓库的 `.gitignore` **必须**显式排除两个代码仓库与工作区辅助目录（与采用布局 A 或 B 无关——两个代码仓库始终是文档仓库的**兄弟目录**，若不在 `.gitignore` 中排除，其内容会被误纳入文档仓库）：

```gitignore
# 代码仓库（各有独立版本控制，不纳入文档仓库）
<项目名>-backend/
<项目名>-frontend/

# 工作区辅助（非交付物）
.workbuddy/
.tmp-research/
```

### R4 仓库命名统一前缀

三个仓库一律以 `necoocean-` 开头（与个人署名约定一致）：

```
necoocean-<项目>-backend
necoocean-<项目>-frontend
necoocean-<项目>-docs
```

### R5 契约唯一事实源

**接口契约的唯一事实源是文档仓库中的《接口清单》**。

- 后端实现与前端调用**都引用它，不在各自仓库里复述契约**。
- **禁止**在后端仓库或前端仓库内维护第二份接口定义文档。
- 前端可从契约生成类型定义（如 TS interface），但那是**构建产物**，须在文件头注明"由《接口清单》生成，勿手改"。

### R6 变更顺序不可颠倒

接口变更流程固定为三步，**顺序不可逆**：

```
① 先改《接口清单》（文档仓库提交）
② 后端实现（后端仓库提交）
③ 前端跟进（前端仓库提交）
```

**理由**：契约先行是"前后端分离"能并行开发的前提。若允许后端先改再补文档，前端的联调依据就会短暂失效，退化为"猜接口"。

### R7 发布关联须记录

每次对外发布，须在文档仓库维护一张**版本对应表**：

| 发布日期 | 文档版本 | 后端 tag | 前端 tag |
|---|---|---|---|
| YYYY-MM-DD | PRD vX.Y | `vX.Y.Z` | `vX.Y.Z` |

**载体**：文档仓库的 CHANGELOG（见 `质量与交付类文档规范.md` §四）。

**理由**：三仓库分离后，"某次发布用的是哪版需求"这个问题的答案分散在三个仓库，必须有一处集中记录，否则日后无法复现。

## 五、跨仓库的三条纪律

R5~R7 是硬约束，以下三条是配套工作纪律：

| # | 纪律 | 不做会怎样 |
|---|---|---|
| 1 | **不存在"顺手改一下"的跨仓库改动** | 若一次改动需同时动两个仓库，说明契约未定清——应回到 R6 第①步重新冻结接口 |
| 2 | **每个仓库的 README 只写自己** | 后端 README 不描述前端构建流程（引用文档仓库即可），避免三处复述导致口径漂移 |
| 3 | **文档仓库承接全部决策留痕** | ADR、参数台账、验收用例全部在文档仓库；代码仓库只记"实现了什么"，不记"为什么这么定" |

## 六、新项目落地清单（可直接执行）

新建一个前后端分离项目时，按序执行：

| 序 | 动作 | 验收点 |
|---|---|---|
| 1 | 建工作区目录 `<项目名>/` | 目录存在，**内部无 `.git`** |
| 2 | 建 `<项目名>-backend/`，`git init`，关联 remote | `git remote -v` 指向正确仓库；首个提交成功 |
| 3 | 建 `<项目名>-frontend/`，`git init`，关联 remote | 同上 |
| 4 | 建 `<项目名>-docs/`，`git init`，关联 remote | 同上 |
| 5 | 按 §3.1 建三个子目录（**新建项目一律布局 A**） | 在文档仓库根下建 `docs/` 中间层，其内建 `doc/`、`design/`、`文档规范/` 三个子目录。从本仓库复制一份 `文档规范/` 作为起步 |
| 6 | 写工作区根 `README.md`（说明三仓库结构，不纳入版本控制） | 文件存在且未被任何仓库跟踪 |
| 7 | 建 `<项目名>-docs/CHANGELOG.md`（含版本对应表） | 表头存在，初版留空 || 8 | 校验：三个仓库均能独立 `git status` 且互不感知 | 在任一仓库内看不到另两者的未跟踪文件 |

> **第 8 步是最易漏的验收点**。若在某仓库的 `git status` 中看到了兄弟目录的文件，说明 R1 或 R3 未落实。

## 七、与既有文档的关系

| 项 | 说明 |
|---|---|
| 与《前后端分离架构说明》§十 第 3 项的关系 | 该项定稿为"前后端两个独立仓库"，**本规范是其扩展**：补入第三个文档仓库，并明确工作区不做仓库 |
| 与 ADR 的关系 | 本规范属**跨项目工程约定**，不属单一项目的设计决策，故独立成文而非写入某项目 ADR。若某项目需偏离，须在该项目文档仓库内新建 ADR 记录偏离理由 |
| 与《文档撰写通用规范》的关系 | 本文是其**分类补充**（针对"仓库形态"这一命题），层级平行于《设计与接口类文档规范》等 |
| 与 N-2《部署运维手册》的关系 | 部署手册中的"从哪个仓库取什么产物"须与本规范的仓库划分一致 |

## 八、适用范围与边界

### 8.1 适用

- ✅ 一切**前后端分离**的个人项目（前端独立构建、后端提供 API）
- ✅ 项目规模从零到中等，**单人开发**
- ✅ 前后端**零代码共享**

### 8.2 不适用（须单独论证）

| 情形 | 处置 |
|---|---|
| 前后端共享代码（如共用类型定义包、共用构建工具链） | 不适用本规范，须单独论证仓库形态 |
| 纯后端项目 / 纯静态站点 | 不适用"三仓库"；文档仓库仍建议单独建立 |
| 多人协作且需要原子提交跨模块改动 | 可复议 monorepo，须记录论证过程 |
| 已有历史项目运行良好 | **不强制改造**；若确需改造（如统一为新项目的布局 A），须完成全量路径引用校验并记录于 CHANGELOG。**本仓库已于 2026-09-21 完成该改造** |
| 文档仓库需迁布局（A ↔ B） | 非禁止，但须评估路径引用改写成本（见 §3.1） |

### 8.3 规范自身的修订

本规范属「文档规范」目录（本仓库实际路径 `docs/文档规范/`），其修订适用 `docs/文档规范/README.md` §六 的规则：**修订后须检查各分类规范之间的引用是否仍有效**。
