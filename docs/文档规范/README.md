# 文档规范

**版本**：v1.9
**生效日期**：2026-09-21
**维护人**：NecoOcean
**适用范围**：`necoocean-vault` 仓库内一切 Markdown 文档，以及未来同类个人项目

---

## 一、本目录的定位

本目录是**文档撰写与图表的唯一判据来源**。在此规范落盘之前，仓库内不存在成文的撰写标准——文档的口径、结构、编号、章节命名均由多轮迭代各自形成，导致同类信息在不同文档间出现偏差（示例：留言状态在 PRD 为 4 种、在功能清单为 2 种；实体外键数在正文记为 4 条而实际为 5 条）。

本规范的作用是**把隐含约定显式化**，使"文档合规"具备可判定性。

> **判定纪律（全局适用）**：任何合规判定必须能定位到 **文件 + 章节 + 行号**。不接受"看起来还行""基本一致"这类表述——它们不可验收。

## 二、文件清单

| 文件 | 覆盖文档类型 | 何时必读 |

### 2.3 工程约定规范（跨项目强制）

| 文件 | 内容 | 何时必读 |
|---|---|---|

### 2.4 图表与绘图规范

| 文件 | 内容 |
|---|---|
| `文档图表绘制规范.md` | ASCII 框图与 Mermaid 的语法层规范：字符集白名单、节点与连线、命名与图例、布局对齐（显示列宽）、Mermaid 转换规范、21 项校验清单 |
| `绘图prompt.md` | AI 绘图工具的 Prompt 库（位图输出）：9 条提示词条目、通用负面 Prompt、自定义替换规则、选用优先级 |

> **引用前缀约定（2026-09-21 立）**：本目录内引用规范文件用**裸文件名**（同目录）；引用 `docs/doc/` 下文档时**必须带分类目录前缀**，如 `docs/doc/02-设计与实现/系统设计文档.md`。分类明细见 §4.1.1。

> **两者的分工必须分清**：`文档图表绘制规范.md` 管**文档内嵌的结构化图表**（ASCII / Mermaid，矢量、可版本控制）；`绘图prompt.md` 管**交给 AI 绘图工具生成的位图插图**（用于 PPT、Word、封面）。二者共享同一视觉基调（扁平矢量、蓝绿配色、无渐变阴影装饰、对齐规整），但输出形态与技术手段完全不同，**不可互相替代**。

> - **验收用例**（编号 `B-xx`）属**验收阶段**产物，与《测试用例集》（N-1）成对使用，而与"需求描述"不同层。
>
> 二者独立后，PRD 保持纯粹的"需求事实源"定位；`A-xx` / `B-xx` 编号体系**继续保留**，只是其载体从"PRD 附录"变为独立文件。
>
> **实证**：PRD 曾因参数持续回填，版本号从 **v1.1 连推至 v1.7**——正是"参数挂在需求文档下"导致版本号被动高频跳动。

> **优先级建议**：**N-2 部署运维手册**与**N-3 CHANGELOG** 为最紧缺口——前者是"一期不公开上线"前提下唯一能让部署可复现的载体，后者在进入开发后将立即产生高频更新需求。

## 四、文档目录与命名约定

### 4.1 目录结构

> **本节仅描述「文档仓库」内部结构**。文档仓库在工作区中的位置、以及它与前后端仓库的关系，见 `仓库形态规范.md`。

```
necoocean-vault/                 # ← 文档仓库根（工作区三仓库之一）
├── README.md                    # 项目总览（N-4，待建）
├── CHANGELOG.md                 # 跨文档变更记录 + 版本对应表（N-3，待建）
└── docs/                        # ← 仓库内文档根
    ├── doc/                     # 需求、设计、进度类文档（按生命周期分四类）
    │   ├── 01-需求与范围/       # PRD、一期清单、ADR
    │   ├── 02-设计与实现/       # 系统设计、架构、接口、选型、参数台账、验收用例
    │   ├── 03-进度与交付/       # 进度分析、测试用例集、部署运维手册（后两项待建）
    │   └── _archive/            # 快照类文档，不随项目更新，仅作追溯
    ├── design/                  # UI 设计交付物（规范 + 原型）
    └── 文档规范/                # 撰写、图表、工程约定规范
```

> **本仓库采用布局 A**（`仓库形态规范.md` §3.1）：文档仓库根下含 `docs/` 中间层，`doc/`、`design/`、`文档规范/` 三个子目录位于 `docs/` 内。该布局于 **2026-09-21 自布局 B 迁入**，并完成全量路径引用校验（14 个文件、78 处引用）。
> 故本文档中出现的 `docs/doc/…`、`docs/design/…`、`docs/文档规范/…` **即为真实路径**（相对文档仓库根）。新建项目一律采用本布局。

#### 4.1.1 `doc/` 内的四个分类（2026-09-21 立）

分类判据为**读者群 + 更新节奏**（沿用本文档 §2.2 对"为何拆出待确认参数台账与验收用例集"的同一判据）：

| 目录 | 读者 | 更新节奏 | 收录 |
|---|---|---|---|
| `01-需求与范围/` | 需求方、产品视角 | 定稿后趋于稳定 | PRD、一期清单、ADR |
| `02-设计与实现/` | 设计、开发 | 随迭代高频更新 | 系统设计、架构说明、接口清单、技术选型、参数台账、验收用例集 |
| `03-进度与交付/` | 本人、项目管理视角 | 阶段性覆盖 | 进度分析、测试用例集（N-1）、部署运维手册（N-2） |
| `_archive/` | 追溯用 | **不更新** | 各轮审查报告、检查报告等一次性快照 |

**两条纪律**：

1. **文档不直接放在 `doc/` 根下**——新增文档必须归入上述某一分类，否则分类会随文件增长而失效。
2. **`_archive/` 内文档不作事实源**——其结论若被采纳，须回填至 01/02/03 中的相应文档；`_archive/` 只在追溯"当时是怎么判断的"时查阅。

### 4.1.2 引用路径的三条规则（2026-09-21 立）

| 场景 | 写法 | 例 |
|---|---|---|
| 引用**同目录**文档 | **裸文件名** | 在 `01-需求与范围/` 内引 PRD：`` `个人工具展示网站需求文档（PRD）.md` `` |
| 引用**跨目录**文档 | **仓库根相对完整路径** | `` `docs/doc/02-设计与实现/系统设计文档.md` `` |
| 引用 `docs/文档规范/` 内文档 | 规范目录**内部**用裸名；规范目录**外部**用完整路径 | `README.md` ↔ `docs/文档规范/README.md` |

> **编号不复用、目录可增减**：分类目录的序号（01/02/03）仅用于排序，**不表示优先级**；未来若某类文档增长到难以浏览，可再细分二级目录，但须同步更新本节。

> **说明**：三条规则**判据是"引用点与目标的相对位置"**，而非引用方向。跨目录引用必须写全，原因有且仅有一个：**搜索"哪些文档引用了系统设计文档"时，只有完整路径能一次命中**；裸文件名会随同目录文件增长而歧义。

### 4.2 文件命名规则

| 规则 | 说明 | 正例 | 反例 |
|---|---|---|---|
| 用中文全称 | 文档面向人读，中文可读性优于英文缩写 | `docs/doc/02-设计与实现/系统设计文档.md` | `sdd.md` |
| 不加版本号 | 版本在文档头部记录，不进文件名 | `需求文档（PRD）.md` | `PRD-v1.7.md` |
| 不加日期 | 日期在头部元信息块记录 | `部署运维手册.md` | `部署运维手册-20260921.md` |
| 附录用全角冒号或连字符 | 保持一种风格，不混用 | `docs/doc/02-设计与实现/附录C-接口清单与统一约定.md` | `附录C：接口清单.md` |
| 同一系列加序号后缀 | 便于排序识别 | `docs/doc/_archive/需求文档审阅报告-第二轮.md` | `docs/doc/_archive/审阅报告2.md`（反例：既简写又丢系列名） |

### 4.3 已作废内容的处置

**规则：作废内容不删除，但必须迁出主目录。**

- 在正文内就地作废：保留原文 + 加删除线 `~~...~~` + 加醒目作废标注（含日期与原因）。
- 整节/整篇作废：移入 `docs/doc/_archive/`，主文档中以一行指向 `_archive/` 的说明替代。
- **禁止**在主文档中长期保留"大段已作废但未标注"的内容——这会造成实施者误读。

> **本仓库现存待处置项**：`docs/doc/02-设计与实现/技术选型与工程结构（方案对比）.md` 的 §三（技术栈决策留痕）与 §五（目录结构）含 Thymeleaf 时代产物（`PageController` + `templates/`），虽有醒目作废标注，仍建议迁入 `docs/doc/_archive/`。

## 五、文档生命周期

```
提案 → 起草（草稿版 v0.x）→ 评审 → 定稿（v1.0+）→ 变更维护 → 作废归档
```

| 阶段 | 版本号 | 文档头部"文档状态"写法 |
|---|---|---|
| 起草 | `v0.x` | `**草稿，参数待确认（N 项）**` |
| 评审中 | `v0.x` | `**待评审，可提请冻结**` |
| 定稿 | `v1.0+` | `**已定稿，无未决项**` |
| 变更维护 | `v1.x` | `**已定稿；本版改动：……**` |
| 作废 | 冻结 | `**已作废（YYYY-MM-DD），本文仅作决策留痕，请勿按此实施**` |

**关键纪律**：文档头部必须显式声明"当前是否还有未决项，共几项"。这是本仓库既有文档最值得保留的约定之一——它让"能不能开工"这件事在打开文档 5 秒内就有答案。

## 六、规范自身的使用与维护

1. **新建文档前**：读本文 §三 定位文档类型 → 读对应分类规范 → 读 `文档撰写通用规范.md`。
2. **文档写完前**：对照 `文档撰写通用规范.md` §十 的检查清单逐项核验。
3. **图表绘制前**：读 `文档图表绘制规范.md`；需 AI 绘图插图时读 `绘图prompt.md`。
4. **新建前后端分离项目前**：读 `仓库形态规范.md`，按其 §六 落地清单执行，完成后对照 §九 检查清单（K1~K10）核验。
5. **规范修订**：本目录内文档的修订同样适用上述版本与修订记录规则；修订后须检查各分类规范之间的引用是否仍然有效。
