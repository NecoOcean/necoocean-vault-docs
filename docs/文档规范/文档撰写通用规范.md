# 文档撰写通用规范

**版本**：v1.0
**生效日期**：2026-09-21
**适用范围**：`necoocean-vault` 仓库内一切 Markdown 文档
**规范来源**：由既有 9 份文档的实际撰写方式归纳提炼，非外部引入

---

## 零、本规范的核心命题

本仓库既有文档的可读性**不来自文采，来自纪律**。归纳出的五条支柱：

| 支柱 | 内涵 | 反例（本仓库真实出现过的） |
|---|---|---|
| **① 结论先行** | 每份文档、每个大章开头先给可执行的结论，再展开论证 | —— |
| **② 事实源唯一** | 每类信息指定唯一的权威文档，其余文档引用而非复述 | 留言状态在 PRD 是 4 种、在清单是 2 种 |
| **③ 口径显式化** | 模糊词必须落成可测量的条件 | 原"打开延迟≤1.5s""无卡顿" |
| **④ 不确定性标注** | 已决策 / 待确认 / 建议值三种状态必须可区分 | —— |
| **⑤ 变更可追溯** | 每次改动记录"位置 + 改了什么 + 为什么" | —— |

以下各章即这五条支柱的操作化。

## 一、文档头部元信息块（强制）

### 1.1 标准形态

每份文档**第一行是 H1 标题，紧随其后是一个无序列表形式的元信息块**，不加小标题、不空行隔断：

```markdown
# 系统设计文档（System Design Document）

- **文档版本**：v1.0
- **创建日期**：2026-09-21
- **最后更新**：2026-09-21（本次更新摘要）
- **文档状态**：**由既有已定稿文档综合导出，无新增未决项**
- **文档定位**：本文是**面向开发落地的"怎么搭"文档**。架构决策的**事实源**仍是《前后端分离架构说明》v1.2
- **本文不做什么**：不重新论证技术选型、不引入新决策、不改变任何既有约定
- **关联文档**：`docs/doc/02-设计与实现/前后端分离架构说明.md` v1.2 · `docs/doc/01-需求与范围/个人工具展示网站需求文档（PRD）.md` v1.7 · ...

---
```

### 1.2 各字段的撰写要求

| 字段 | 必填 | 要求 |
|---|---|---|
| **文档版本** | ✅ | `v主.次`。初始稿 `v0.1`；定稿 `v1.0` |
| **创建日期** | ✅ | `YYYY-MM-DD` |
| **最后更新** | ✅ | `YYYY-MM-DD（一句话摘要）`，摘要须说明**改了什么**而非"优化完善" |
| **文档状态** | ✅ | **必须显式回答"还有无未决项"**。三种标准写法见 §1.4 |
| **文档定位** | ✅ | 本文解决什么问题、**不**解决什么问题 |
| **本文不做什么** | 建议 | 显式排除越界内容。这是防止文档膨胀与职责重叠的最有效手段 |
| **关联文档** | ✅ | 逐份列出并**标注版本号**。版本号是判断引用是否失效的唯一依据 |
| **决策人 / 检查日期** 等 | 按类 | 决策记录类加"决策人"，报告类加"检查日期""检查范围" |

### 1.3 交叉引用格式

- 文档间引用：用**行内代码 + 文件名**，如 `docs/doc/02-设计与实现/前后端分离架构说明.md`
- 章节引用：`《前后端分离架构说明》§十一`
- 版本引用：`附录C v0.8`（若无版本号，读者无法判断引用是否过期）
- **禁止**写"见上文""如前所述"——跨章节阅读时无从定位

### 1.4 「文档状态」的三种标准写法

| 状态 | 写法 |
|---|---|
| 有未决项 | `**参数未全部定稿：待确认 N 项（见 待确认参数台账）**` |
| 无未决项 | `**无未决项，可启动脚手架**` |
| 已作废 | `**已作废（2026-09-21），仅作决策留痕，请勿按此实施**` |

> **为什么这条最重要**：它把"能不能开工"这个决定，从"通读全文后判断"降为"打开文档 5 秒内可见"。本仓库全部高质量文档都遵守了这条。

## 二、修订记录

### 2.1 简表形态（改动少的文档）

紧随元信息块之后，H2 标题 `## 修订记录` + 三列表格：

```markdown
## 修订记录

| 版本 | 日期 | 说明 |
|---|---|---|
| v1.0 | —— | 初稿 |
| v1.1 | 2026-09-20 | 落实 ADR-001、ADR-002 两项设计决策；补齐 4 项 P0 遗漏 |
| **v1.7** | 2026-09-21 | **附录A A.2 全部定稿，PRD 不再有未决参数** |
```

- 最新一版**加粗**
- "说明"列写**变更内容**，不写"优化""完善""调整"这类空洞词

### 2.2 逐项表形态（改动多的文档）

当单版改动超过约 5 项时，另起逐项表，编号**跨版本连续递增**：

```markdown
**v1.4 逐项改动（2026-09-21）：**

| # | 位置 | 改动 |
|---|---|---|
| 42 | 头 / 9.1 | 部署方案具体化：腾讯云轻量应用服务器（上海五区，4C4G / 3 Mbps） |
| 43 | 9.1 | 新增带宽约束条目：3 Mbps ≈375 KB/s |
```

| 列 | 要求 |
|---|---|
| **#** | 全文档连续编号，从 1 开始，**不按版本重置** |
| **位置** | 章节号或字段名，可定位 |
| **改动** | 写明从什么改到什么；关键项加粗 |

### 2.3 变更摘要块（架构级反转时）

当某版发生**方向性变更**（如架构模式反转）时，在修订记录下方追加引用块，说明前因后果：

```markdown
> **v0.3 变更摘要（2026-09-21 14:55）**：NecoOcean 明确要求**严格前后端分离**。
> 因此：① **移除 Thymeleaf**；② §三 与 §五 作废；③ 前端定为 Vue 3 + Vite。
>
> **注意**：v0.1 的三方案对比与 v0.2 的 Thymeleaf 选型均已作废，保留仅为决策留痕，**请勿按此实施**。
```

**纪律**：作废必须写"为什么作废"与"按什么实施"，否则读者无法判断该信哪一版。

## 三、结论先行

### 3.1 标准形态

每份文档第一个 H2 章节固定为**结论先行**（或"一、结论先行"），用一段话 + 表格给出全貌：

```markdown
## 一、结论先行

**一句话**：这是一个**单机同源部署的严格前后端分离应用**——前端 Vue 3 SPA 只负责渲染与交互，后端 Spring Boot 只输出 JSON。

**系统由 4 个部署单元组成**：Nginx（唯一公网入口）、Spring Boot 应用、MySQL 8、腾讯云 COS。

**两条必须贯穿全系统的设计主线**：

| 主线 | 内涵 | 受影响模块 |
|---|---|---|
| **① 3 Mbps 带宽约束** | 源站出网 ≈375 KB/s 是**本项目最紧的物理约束** | 前端构建、Nginx、资源文件 |
| **② 邮箱与对象键白名单** | 公开接口在**序列化阶段**白名单输出 | 留言反馈、资源文件 |

**当前状态**：**无未决项，可启动脚手架**。
```

### 3.2 要求

1. 第一句必须是**完整的一句话陈述**（"这是一个……"），读者读完这句就知道文档主旨。
2. 关键数字、关键结论**加粗**。
3. 若有必须先声明的风险或代价，在本章内**主动说出**，不藏在后文。
4. 严禁以"在当今……""随着……的发展"开场。

## 四、不确定性标注体系

### 4.1 标记符号（全文统一）

| 标记 | 含义 | 使用要求 |
|---|---|---|
| ✅ | **已决策** | 须注明决策日期与来源（如 `✅ 已确认（2026-09-21）`） |
| ⚠️ | **待确认 / 建议值** | 必须给出建议值及理由，使读者可先按建议值推进 |
| 🔒 | **敏感字段或安全约束** | 用于标注须落实白名单/脱敏的位置 |
| 🔀 | **分期实现项** | 用于标注一期简化版 / 二期完整版的差异 |
| 🆕 | **本版新增** | 用于版本间快速识别 |
| ➖ | **已作废留痕** | 保留但不参与判定 |
| ★ | **关键约束** | 全文级重要约束 |

### 4.2 三种状态的表述纪律

| 状态 | 正确写法 | 禁止写法 |
|---|---|---|
| 已决策 | `✅ 并发口径定为"持续请求节奏下的虚拟用户数"（A-16）` | `并发大概是 50 左右` |
| 待确认 | `⚠️ 建议 12 小时（个人站，兼顾安全与免重复登录）；按建议值可先实现` | `会话有效期待定` |
| 建议值 | `⚠️ 建议 **100**` | `100 左右吧` |

**核心纪律（NecoOcean 明确要求）**：**绝不把推测表述为事实**。没有证据的项一律归入"待确认"，不得因"通常都会有"而默认已具备。

## 五、口径显式化（可验收性）

### 5.1 反面模式

| 反面表述 | 问题 |
|---|---|
| "功能完整无 BUG" | 不可验收 |
| "打开延迟 ≤1.5s" | 未定义测量条件（首屏还是接口？并发多少？网络环境？） |
| "≥50 并发" | 未定义并发口径（瞬时返回？持续节奏？） |
| "快很多""降低约 40%"（无基线） | 无基线，不可复算 |
| "完成后检查一下" | 无判据 |

### 5.2 正面模式：指标必须带口径

```
指标 = 被测量对象 + 阈值 + 测量条件 + 达标边界
```

**范例（本仓库实际采用）**：

| 层次 | 表述 |
|---|---|
| ❌ | 首屏加载 P75 ≤1.5s |
| ✅ | 首屏完整加载 **P75 ≤1.5s**，**达标场景为并发峰值 ≤3 人**，首屏 gzip 体积 **≤163 KB**（JS ≤130 / CSS ≤15 / HTML ≤3 / API ≤15） |

| 层次 | 表述 |
|---|---|
| ❌ | 支持 ≥50 并发 |
| ✅ | 接口层 **≥50 并发**（口径：**持续请求节奏下的虚拟用户数**，非"同瞬间全部返回"），错误率 <1% |

### 5.3 验收标准的三要素

每条验收项必须包含：

1. **前置条件**：什么状态下执行
2. **操作**：执行什么动作
3. **可观测结果**：看到什么算通过（含具体数值或状态）

```markdown
| 编号 | 前置条件 | 操作 | 预期结果 |
|---|---|---|---|
| B-31 | 站点设置中关闭留言功能 | 访问任意工具专题页 | 留言表单不可见；直接 POST C-07 返回 40300；**既有留言与回复仍正常展示** |
```

## 六、语言与格式

### 6.1 语言风格

| 要求 | 说明 |
|---|---|
| **结论先行 + 结构化依据** | 先给结论，其后是编号列表或分类小节 |
| **量化优先** | 能量化就量化。"降低约 40%"优于"快很多" |
| **客观陈述权衡** | 存在多方案时给出各自优劣，不只给一个未加限定的推荐 |
| **标注适用边界** | 明确"本文的结论在什么前提下成立" |
| **无寒暄、无冗余铺垫** | 不写"接下来让我们看看……" |
| **不空洞赞美** | 不写"这是一个非常棒的设计" |

### 6.2 Markdown 格式约定

| 项 | 约定 |
|---|---|
| 标题层级 | 文档标题 `#`；主章节 `##`；小节 `###`；更深 `####`。**不跳级** |
| 章节编号 | 中文序号 `## 一、` `### 1.1`，或纯数字 `## 1.`——同一文档内统一，不混用 |
| 表格 | 用于字段定义、约束清单、对比、验收项。**列数不建议超过 6 列** |
| 代码块 | 一律标注语言：```` ```json ````、```` ```bash ````、```` ```nginx ````。**无语言标记的代码块仅限 ASCII 图表** |
| 引用块 `>` | 用于"关键提醒""风险提示""设计要点" |
| 加粗 | 用于关键结论、数字、警示。**不用于整段强调** |
| 分隔线 `---` | 用于头部元信息块之后、主章节之间 |
| 转义斜杠 | 本仓库存在 `1\.1` 形式的人工转义，**新文档不采用**——除非确实需要防止 Markdown 将 `1.1` 解析为有序列表 |

### 6.3 术语一致性

**命名唯一性表（本仓库既定）**：

| 概念 | 唯一写法 | 禁止写法 |
|---|---|---|
| 前端 | `Vue 3 SPA` | Vue3、vue、前端应用 |
| 后端 | `Spring Boot` | springboot、SB |
| 对象存储 | `腾讯云 COS`（首现），此后简称 `COS` | cos、腾讯云对象存储（混用） |
| 数据库 | `MySQL 8` | mysql、MySQL8 |
| 部署四单元 | 顺序固定：浏览器 → Nginx → Spring Boot → COS | 任意顺序 |
| 中国香港/中国澳门/中国台湾 | 三分表述 | 单独列为国家 |

术语表见 `docs/doc/02-设计与实现/术语表.md`（N-7，待建）。

## 七、编号体系

| 前缀 | 用途 | 载体文档 | 示例 |
|---|---|---|---|
| `A-xx` | 待确认/已确认参数 | `待确认参数台账`（独立文档） | `A-16` |
| `B-xx` | 验收用例 | `验收用例集`（独立文档） | `B-31` |
| `C-xx` | 接口条目 | `附录C-接口清单与统一约定` | `C-07` |
| `D-xx` | 遗留/待决策项 | `UI设计规范` §十一 | `D-7` |
| `Q-x` | 向用户提出的问题 | 决策过程记录 | `Q-5` |
| `ADR-xxx` | 设计决策记录 | `设计决策记录-*` | `ADR-001` |
| `I-x` / `OOS-x` | 范围内 / 范围外条目 | ADR §2 | `I-1` |
| `N-x` | 文档类型编号（仅规范目录使用；含已建成项，编号不复用） | `docs/文档规范/README.md` §三 | `N-11`（已建成） |

**纪律**：
- 编号**一经分配不得复用**，即使条目被删除。
- 编号在同一文档内**连续且唯一**。
- 跨文档引用编号时须带**载体文档名**，如 `待确认参数台账 A-16`、`验收用例集 B-31`。

> **重要（2026-09-21 立）**：`A-xx` 与 `B-xx` **不再以 PRD 附录形式存在**，已改为独立文档。理由：二者的生命周期与 PRD 不同——参数在全流程被反复查阅且持续增删，验收用例属验收阶段产物。详见 `需求类文档规范.md` §七 / §八。

## 八、图与表的选用

| 信息形态 | 采用 | 依据 |
|---|---|---|
| 字段定义、约束清单、对比、验收项 | **表格** | 字段级完整性要求；可逐行核验 |
| 图论结构（依赖/状态机/时序/ER/上下文） | **Mermaid** | 可版本控制、可渲染、结构可校验 |
| 空间与层级结构（目录树/UI 布局骨架） | **ASCII 框图** | Mermaid 无法表达列对齐 |
| 位图插图（PPT/Word 配图） | **AI 绘图 Prompt** | 见 `绘图prompt.md` |

**图题格式**：单文档 ≥3 图时，每图须加图题：

```markdown
**图 {章节}-{序号}　{标题}**
```

其中章节与序号用半角连字符，**标题前为一个全角空格**。例：`**图 5-1　实体关系**`

**图例触发条件**：图中使用 ≥2 种箭头样式，或出现任何符号标记（`🔒 ★ ⚠️`）时，**必须配图例**，且图例必须与图中符号双向一致。

详细规则见 `文档图表绘制规范.md`。

## 九、术语与解释的位置

1. **首次出现**：术语首次出现时在括号内给简短定义，如"（两阶段直传：前端直传 COS，不经应用服务器）"。
2. **判定总则式解释**：涉及判定的规则（如"什么算 ERROR"），必须写成 **编号列表 + 判定标准**，不能写成散文。
3. **集中维护**：同一术语在多份文档反复解释时，抽出至 `docs/doc/02-设计与实现/术语表.md`（N-7，待建），正文改为引用。

## 十、撰写完成前检查清单（21 项）

- [ ] **A1** H1 标题后紧跟元信息块，七项字段齐全
- [ ] **A2** 「文档状态」显式声明有无未决项及项数
- [ ] **A3** 关联文档逐份标注版本号
- [ ] **A4** 有修订记录，最新版加粗，说明列写具体变更而非"优化"

### B. 内容结构（5 项）

- [ ] **B1** 第一章为「结论先行」，首句是完整陈述
- [ ] **B2** 「文档定位」已写清本文做什么、不做什么
- [ ] **B3** 作废内容有删除线 + 作废标注（日期 + 原因 + 按什么实施）
- [ ] **B4** 无"见上文""如前所述"等不可定位引用
- [ ] **B5** 章节编号风格全文统一，未跳级

### C. 口径与可验收性（5 项）

- [ ] **C1** 所有性能/规模指标带**口径限定**（测量条件 + 达标边界）
- [ ] **C2** 无"功能完整无 BUG""流畅""无卡顿"类不可验收表述
- [ ] **C3** 已决策项标 ✅ 并注明日期与来源
- [ ] **C4** 待确认项标 ⚠️ 并给出建议值 + 理由
- [ ] **C5** 验收项含前置条件 / 操作 / 可观测结果三要素

### D. 一致性（4 项）

- [ ] **D1** 术语符合命名唯一性表（`Vue 3 SPA` / `Spring Boot` / `COS` / `MySQL 8`）
