# 需求类文档规范

**版本**：v1.2
**生效日期**：2026-09-21
**适用范围**：产品需求文档（PRD）、分期功能清单、需求审阅报告、设计决策记录（ADR）、安全与合规说明、待确认参数台账、验收用例集
**上位规范**：`文档撰写通用规范.md`（本文不重复其内容，仅补充各类文档的专有结构）

---

## 一、需求类文档族的关系

这类文档的共同命题是**回答"做什么、不做什么、为什么"**，而不回答"怎么做"（后者属设计类文档）。

```
PRD（需求唯一事实源）
 ├── 分期功能清单 —— 回答"本期做哪些"（PRD 的横切切片）
 ├── ADR 设计决策记录 —— 回答"边界为什么划在这里"（PRD 的判例库）
 ├── 需求审阅报告 —— 回答"当前文档还缺什么"（PRD 的质量快照）
 ├── 安全与合规说明 —— 回答"合法合规的前置条件"（PRD §9 的展开）
 ├── 待确认参数台账 —— 回答"还有什么没定"（跨全流程关注，编号 A-xx）
 └── 验收用例集 —— 回答"怎样算做完"（验收阶段产物，编号 B-xx）
```

**事实源归属（硬性）**：

| 信息 | 事实源 |
|---|---|
| 需求、字段定义 | **PRD** |
| 本期范围 | **分期功能清单** |
| 边界判例与排除项 | **ADR** |
| 合规与备案 | **安全与合规说明**（现暂在 PRD §9） |
| 未决参数及取值 | **待确认参数台账**（`A-xx`） |
| 验收判定 | **验收用例集**（`B-xx`） |

> **两项独立理由（2026-09-21 立）**：`A-xx` 与 `B-xx` 此前作为 PRD 附录存在，但它们的**生命周期与读者群与需求文档不同**——待确认参数在**设计、开发、验收全流程**被反复查阅且持续增删，而 PRD 定稿后应趋于稳定；验收用例属**验收阶段**产物，与《测试用例集》成对使用。独立成文后，PRD 可保持纯粹的"需求事实源"定位，而 `A-xx` / `B-xx` 编号体系**继续保留**。

清单与 PRD 冲突时**以 PRD 为准**，并须同步修订清单。

## 二、产品需求文档（PRD）

### 2.1 标准章节骨架

```
一、项目概述            —— 背景 / 目标 / 目标用户 / 不做什么
二、前台功能            —— 按页面组织
三、页面架构            —— 页面清单、路径、承载内容
四、核心机制            —— 留言 / 下载 / 存储 / 通知（按机制组织，非按页面）
五、非功能需求          —— 性能 / 安全 / 兼容 / 可用性
六、功能分期            —— 一期 / 二期
七、交付物              —— 文档、代码、脚本清单
八、数据实体与字段定义   —— 字段级表格
九、上线前置与合规      —— 备案 / 隐私政策 / 约束清单
```

### 2.2 各章撰写要点

**§一 项目概述**

- 1.1 项目背景：用**第一人称陈述动机**，不写"随着互联网的发展"。
  > 正例："本人自主开发多款轻量化工具产品，目前无统一公开展示、分发、反馈渠道。"
- 1.2 项目目标：编号列表，每条是**可检验的目标**，不是愿景。凡"不做什么"必须在此显式声明并注明依据（如"本站**不提供**文件在线预览（依据 ADR-001）"）。
- 1.3 目标用户：枚举即可，不展开画像。
- 建议增设 **1.4 明确不做**：把范围外能力集中列出，这是防止范围蔓延的第一道闸。

**§二 前台功能**

按**页面**组织（首页 / 专题页 / 关于我 / 全站通用）。每个功能点的写法：

| 要素 | 要求 |
|---|---|
| 展示内容 | 逐项列出字段与元素 |
| 交互规则 | 排序、分页、筛选、叠加规则 |
| 边界处理 | 空态、错误态、缺失态 |
| 不做项 | 就地标注（如"**不做**文件预览、在线编辑、转码、在线运行"） |

**§三 页面架构**

用表格给出**页面清单**：页面名 / 路径 / 承载内容 / 是否一期。一期不单设的页面须显式说明理由。

**§四 核心机制**

这是 PRD 最易失手的部分。**机制类章节必须给出：定义 + 字段 + 可见性 + 全链路行为 + 已知限制**。

范例（留言机制的写法）：

```markdown
### 4.2 留言机制

**字段定义**
| 字段 | 必填 | 可见性 | 说明 |
|---|---|---|---|
| 昵称 | 否 | 公开 | 留空显示"匿名访客" |
| 邮箱 | 否 | **仅管理员** | 用于反馈处理结果，不公开 |
| 分类 | 是 | 公开 | 4 类：使用体验/功能建议/BUG报错/问题咨询 |
| 内容 | 是 | 公开 | ≤1000 字 |
| 复现步骤 | BUG 类必填 | 公开 | 结构化字段 |

**可见性约束**：公开接口须在**序列化阶段**白名单输出，不得返回 `contact_email`。

**已知限制**：一期无回复通知，用户需自行回访查看。
```

> **纪律**：机制类章节必须写明**已知限制**。本仓库的 ADR-002 正是从"回复无通知"这一限制被明确写出后，才衍生出"一期不发任何邮件"的决策。

**§五 非功能需求**

性能指标必须满足 `文档撰写通用规范.md` §五 的口径要求。安全需求须逐条给出**实现位置**（如"公开接口字段排除""上传目录禁止执行"）。

**§七 交付物**

表格列举：交付物名称 / 形式 / 说明。**这是验收范围的法律边界**——凡不在表内的，不属于本期交付。

**§八 数据实体与字段定义**

字段表格式（强制）：

```markdown
#### 8.5 messages（留言）

| 字段 | 类型 | 允许空 | 默认 | 说明 |
|---|---|---|---|---|
| id | bigint | 否 | AUTO_INCREMENT | 主键 |
| tool_id | bigint | 否 | —— | FK → tools.id |
| contact_email | varchar(254) | 是 | NULL | ⚠️ 仅管理员可见，公开接口排除 |
| audit_status | tinyint | 否 | **2** | 1=待审核 2=已通过 3=已拒绝 |
| keyword_flagged | tinyint(1) | 否 | 0 | 关键词命中标记 |
| content | text | 否 | —— | ≤1000 字 |
| created_at | datetime | 否 | CURRENT_TIMESTAMP | —— |

**索引**：`(audit_status, created_at)`、`(is_pinned, created_at)`
```

| 要求 | 说明 |
|---|---|
| 每个字段必须有**类型 + 允许空 + 默认值 + 说明** | 缺任一列即不合规 |
| 枚举字段必须列出**全部取值及含义** | 避免"状态"在不同文档口径不一 |
| 分期字段须标注 | 如 `audit_status` 注明"一期默认置 2" |
| 敏感字段加 🔒 或 ⚠️ | 并说明脱敏/排除要求 |
| 索引与唯一约束独立成节 | 见 §8.9 |
| **实体数、外键数等汇总数字必须与图一致** | 本仓库曾出现正文写"4 条外键"而实际 5 条的偏差 |

**§九 上线前置与合规**

必须覆盖：ICP 备案（归属地 + 与服务器所在地无关的说明）、隐私政策、数据保留与删除、内容审核机制、带宽/流量约束清单。

## 三、分期功能清单

### 3.1 定位

清单**不是 PRD 的缩写版**，而是**范围切片**：它回答"本期做 / 本期不做"，并给出每一项的口径归属。

### 3.2 标准骨架

```
一、整体定位（极简总结）      —— 3~5 行，含架构口径引用
   设计边界（已确认项）        —— 引用 ADR
   技术方案（已确认项）        —— 引用 PRD / 选型文档
二、前台核心功能（必须上线）
三、后台核心功能（必须上线）
四、本期明确不做
五、待确认项（或：已全部定稿）
A.1 已定稿参数
A.2 仍待确认（定稿后须清空）
```

### 3.3 写作纪律

| 纪律 | 说明 |
|---|---|
| **每项功能只写要点，不重复 PRD 描述** | 用 `（见 PRD §x.x）` 指向事实源 |
| **必须标注"不做"边界** | 引用 ADR 排除项编号（如"不含在线预览（I-1~I-7 之外）"） |
| **参数改动必须在清单同步** | 本仓库清单 v1.4~v1.7 每版都注明"对齐 PRD vN" |
| **章节末尾给"已定稿参数"列表** | 使阶段结论可一眼确认 |

> **常见失手**：清单中写"纯静态展示 + 后台管理"——与"文件上传""留言写入"逻辑互斥。**任何自相矛盾的表述都必须当场消解，不能留到开发阶段。**

## 四、需求审阅报告

### 4.1 定位

审阅报告是**质量快照**，不是长期维护文档。它记录"某一时点发现的问题"，问题闭环后**不再回填**，而是新建一轮报告。

### 4.2 标准骨架

```
检查范围与判据
一、覆盖度评估           —— 给出百分比 + 缺口清单
二、问题分类清单         —— 按 遗漏 / 模糊 / 矛盾 三类
三、逐条结论与建议       —— 可执行、可验收
四、闭环状态
```

### 4.3 问题三分类（强制）

| 分类 | 定义 | 处置 |
|---|---|---|
| **遗漏** | 应有而没有 | 补充内容 |
| **模糊** | 有表述但不可判定 | 落成可测量条件 |
| **矛盾** | 两处表述互斥或口径不一 | 消解冲突，指定事实源 |

**每条问题必须包含**：编号 / 位置（文档 + 章节）/ 现象 / 影响 / 具体建议。

**纪律**：
- 不接受"建议完善""建议优化"这类不可执行表述。
- 覆盖度用**百分比 + 缺口条目**表达，不用"基本完整"。
- **第二轮报告新建文件**，不改写第一轮——保留审阅轨迹。

## 五、设计决策记录（ADR）

### 5.1 定位

ADR 是**判例库**。当范围出现争议（"给 APK 生成二维码算不算预览？"），ADR 应能直接给出裁定而无需重新讨论。

### 5.2 标准骨架（每个 ADR 一节）

```
# ADR-00x：{决策主题}

## 1. 定义          —— 一句话给出精确定义
## 2. 范围边界
   ### 2.1 在范围内（In Scope）    —— I-x 编号表
   ### 2.2 明确排除（Out of Scope） —— 编号列表，逐条可裁定
   ### 2.3 边界判例                —— 易混淆场景的裁定表
## 3. 实现约束       —— 分层给出（存储层 / 接口层 / 运维层）
## 4. 影响与代价     —— 诚实标注代价
```

### 5.3 写作纪律

| 纪律 | 说明 |
|---|---|
| **定义必须是"严格限定为……"句式** | 不含模糊修饰 |
| **排除项必须逐条编号** | 便于 PRD 与清单引用 |
| **必须写边界判例表** | 含"场景 / 裁定 / 依据"三列，这是 ADR 最有价值的部分 |
| **必须诚实标注代价** | 如"直传只是把文件绕开了应用服务器，**并没有绕开带宽**" |
| **决策人 + 状态必须显式** | 决策人 NecoOcean；状态"已确认" |
| **派生决策另起小节** | 主决策与由它派生的技术决策分开记录 |

## 六、安全与合规说明（N-9，待建）

### 6.1 当前状态

合规内容现散落在 `PRD §9`、`ADR-002` 与 `清单` 中，无独立文档。**建议独立**，理由：合规内容是**对外承诺**（隐私政策文案）与**法律前置**（ICP 备案）的混合体，与需求迭代节奏不同，独立后更易维护。

### 6.2 建议骨架

```
一、ICP 备案            —— 归属地、材料、与服务器所在地无关的说明
二、隐私政策要点         —— 收集什么、为何收集、如何存储、如何删除
三、数据保留与删除策略    —— 保留周期、删除触发、导出与审计
四、内容审核机制         —— 策略分期、关键词标记、人工复核
五、安全约束清单         —— 白名单、限流、鉴权、CSRF
六、未成年人保护
七、免责声明
```

### 6.3 撰写要点

- **备案归属地按主体归属地受理，与服务器所在地无关**——此点须显式写明，本仓库曾因此产生疑问。
- 隐私政策中的字段说明必须与 PRD §8 的字段定义一致。
- 涉及地域表述时，中国香港 / 中国澳门 / 中国台湾须为三分形式。

## 七、待确认参数台账（N-11，独立文档）

### 7.1 定位

**回答"还有什么没定、按什么值先做"**。它是**全流程**文档——设计、开发、验收各阶段都需查阅，因此**不挂在 PRD 之下**。

> **为何独立**：参数在决策过程中**持续增删**，而 PRD 定稿后应趋于稳定。二者更新节奏不同，合在一处会导致 PRD 版本号被动高频跳动（本仓库 PRD 曾因参数回填连推 v1.1→v1.7）。

**落点**：`docs/doc/02-设计与实现/待确认参数台账.md`

### 7.2 标准骨架

```
一、状态总览            —— 未决 N 项 / 已决 M 项；一句话结论
二、未决参数（⚠️）      —— 逐条给建议值 + 理由
三、已决参数（✅）      —— 逐条给结论 + 决策日期 + 落点
四、已作废参数（➖）    —— 保留留痕，不复用编号
```

### 7.3 条目格式（强制）

| 列 | 要求 |
|---|---|
| **编号** | `A-xx`，**一经分配不复用**（即使条目作废） |
| **参数** | 参数名，须与正文称呼一致 |
| **取值 / 建议值** | 已决写结论；未决写建议值**并给出理由** |
| **状态** | ✅ 已决策 / ⚠️ 待确认 / ➖ 已作废 |
| **决策日期** | 已决项必填 |
| **落点** | 该取值被写入哪份文档的哪一节——**这是可追溯性的关键** |

**范例**：

```markdown
| 编号 | 参数 | 取值 | 状态 | 决策日期 | 落点 |
|---|---|---|---|---|---|
| A-16 | 并发口径 | "≥50 并发"= 持续请求节奏下的虚拟用户数；首屏达标场景为并发峰值 ≤3 人 | ✅ | 2026-09-21 | PRD §5.1 |
| A-21 | 日志保留周期 | ⚠️ 建议 30 天（单文件 100 MB 轮转） | ⚠️ | —— | 待落 PRD §9.1 |
```

### 7.4 撰写纪律

| 纪律 | 说明 |
|---|---|
| **编号不复用** | 条目作废后编号保留在"已作废"区，不得回收给新参数 |
| **未决项必给建议值** | 使开发可先按建议值推进，不因未决而阻塞 |
| **已决项必标落点** | 无落点的参数等于"决定了但没写进任何文档"，必然会丢 |
| **文档头部须显式声明剩余项数** | 如"未决 0 项"/"未决 3 项"；这是判断能否开工的核心依据 |
| **定稿后未决区须清空** | 若清空，在"状态总览"写明"无未决参数" |
| **变更须记入本文档修订记录** | 而非只改 PRD 修订记录 |

## 八、验收用例集（N-12，独立文档）

### 8.1 定位

**回答"怎样算做完"**。属**验收阶段**产物，与《测试用例集》成对使用（前者是"需求是否满足"，后者是"怎么点怎么验"）。

> **为何独立**：验收用例与需求描述的**层级不同**——需求说"要什么"，用例说"达到什么状态算满足"。且用例集在开发过程中持续追加（本仓库曾一次追加 B-32~B-34 三条），与 PRD 的稳定节奏不一致。

**落点**：`docs/doc/02-设计与实现/验收用例集.md`

### 8.2 标准骨架

```
一、验收范围与口径      —— 关联的 PRD 版本、被测版本、前置条件
二、用例清单            —— 按模块分组，编号 B-xx 连续
三、验收结论记录        —— 每轮验收的通过/未通过统计
```

### 8.3 用例格式（强制三要素）

每条用例必须包含：

1. **前置条件**：什么状态下执行。**不允许写"无"**
2. **操作**：执行什么动作
3. **可观测结果**：看到什么算通过——**含具体数值或状态**

**范例**：

```markdown
| 编号 | 前置条件 | 操作 | 预期结果 |
|---|---|---|---|
| B-31 | 站点设置中关闭留言功能 | 访问任意工具专题页 | 留言表单不可见；直接 POST C-07 返回 40300；**既有留言与回复仍正常展示** |
| B-32 | 站点已登录管理员 | 上传 `.whl` / `.AppImage` / `.deb` 各一个 | 三个文件均上传成功；上传 `.sh` 仍被拒绝 |
```

### 8.4 撰写纪律

| 纪律 | 说明 |
|---|---|
| **编号 `B-xx` 连续且不复用** | 一经分配即固定，删除的用例编号不回收 |
| **必须可判定** | 每条用例的结论只有"通过 / 未通过"两态，无中间态 |
| **禁止**"功能完整无 BUG"式判据 | 这是本仓库明确反对的表述 |
| **性能类用例须引用参数台账的口径** | 如并发口径取自 `A-16`，**不得自创** |
| **验收结论须独立记录** | 用例是"标准"，结论是"某轮执行的结果"，二者分开 |
| **覆盖边界与异常** | 不只验正常路径，须含空态、错误态、越权态 |

## 九、需求类文档完成前检查清单
