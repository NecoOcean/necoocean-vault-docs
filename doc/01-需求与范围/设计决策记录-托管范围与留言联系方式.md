# ADR-001：「托管」的准确定义与实现约束

## 1. 定义

**"托管"严格限定为：文件存储与下载分发。**

本站为工具产物（安装包、脚本包、配置文件、文档）提供**不可编辑的静态存储**，并向访客提供**原始字节流的下载**。除此之外不承担任何在线能力。

该定义的要害在于：存储对象是"用户交付的最终产物（artifact）"，**不是"工程"，也不是"运行环境"**。凡属后两者的能力，一律不在一期范围内。

## 2. 范围边界

边界必须逐条写入 PRD。个人项目最典型的失控方式是"顺手加个功能"——以下排除项是防止范围蔓延的硬约束。

### 2.1 在范围内（In Scope）

| 编号 | 能力 |
|---|---|
| I-1 | 管理员上传文件，并归档到指定工具的指定版本下 |
| I-2 | 同一工具下多版本文件并存；可标记一个"当前推荐版本" |
| I-3 | 访客点击下载，浏览器直接获取原始文件（以附件形式下载，不内联打开） |
| I-4 | 展示元信息：文件名、文件大小、上传时间、适用平台、版本号、校验值（SHA-256） |
| I-5 | 文件缺失或下载失败时给出明确错误提示 |
| I-6 | 后台可查看每个工具的存储占用、可删除历史版本文件 |
| I-7 | 外链型资源：为代码仓库、Web 工具等提供站外跳转链接（仅链接，不代理内容） |

### 2.2 明确排除（Out of Scope）

一期及可见的后续版本均**不做**：

1. **在线预览** —— 不解析、不渲染任何文件内容。包含 PDF、图片、文本、Markdown、代码高亮预览，以及压缩包目录浏览、文件树展示。
2. **在线编辑** —— 不提供任何形式的文件内容修改。
3. **转码／转换** —— 不做格式转换、压缩、解压、重新打包、加密、加壳、签名。
4. **在线运行** —— 不执行、不托管、不代理运行任何脚本或服务。含 Python 沙箱执行、Web 工具内嵌（iframe）在线试用。
5. **仓库托管** —— 不提供 Git 服务，不代理或镜像代码托管平台内容。
6. **分享与协作** —— 无文件分享链接、无有效期控制、无权限分级、无协同。
7. **版本比对** —— 版本号仅作为文件分组标签，不做内容 diff，不做自动回滚。
8. **传输增强** —— 不做断点续传、多线程加速、P2P、离线下载。

### 2.3 边界判例（易混淆场景的裁定）

| 场景 | 裁定 | 依据 |
|---|---|---|
| 工具本身是 Web 应用（纯前端小工具） | 站点**不**内嵌运行，专题页只提供站外链接 | 排除项 4 的直接推论 |
| Python 脚本 | 上传 `.py`／`.zip` 供下载，或给出仓库外链；不做在线执行、不代理安装依赖 | 排除项 4、5 |
| 文件需设密码 | 由管理员在上传前自行加密打包，站点不做服务端加密 | 排除项 3 |
| 想展示 zip 内的文件清单 | 不做——属"预览"范畴；仅展示版本列表 | 排除项 1 |
| 想给 APK 生成二维码方便手机扫码 | **允许**——属展示层的链接生成，不触碰文件内容 | 不构成预览/转码 |

## 3. 实现约束

### 3.1 存储层

- **存储位置（已确认）**：**腾讯云 COS 对象存储**（桶私有读写），**一期经预签名直链分发**；正式公开前接入 CDN 后改为 CDN 签名地址，届时不改业务代码（见 PRD 4.3）。禁止开启公开读；一切访问均经后端签发带时效的凭据。
- **对象键规则**：`<tool_id>/<version>/<uuid>.<ext>`。
  - 不使用用户原始文件名参与路径构造——规避路径穿越、中文与特殊字符、同名覆盖三类问题。
  - 原始文件名仅作为数据库字段保存，下载时通过响应头回填。
- **上传方式**：由后端签发预签名上传凭证，前端直传对象存储，避免 200 MB 文件经过应用服务器的内存与磁盘。
  > ⚠️ **实施前提（2026-09-21 补充）**：直传只是把文件绕开了应用服务器，**并没有绕开带宽**。管理员上传 200 MB 包的实际耗时取决于**本地上行宽带**（家庭宽带上行常为下行的 1/10；按 30 Mbps 上行约 55 秒，按 10 Mbps 约 2.7 分钟）。上传慢属可接受（后台操作，非访客路径），但**不要在验收中用"上传要等很久"判定功能异常**。
- **对象存储地域（2026-09-21 补充，实施必查）**：建桶时**必须选择与轻量服务器相同的地域（上海）**。跨地域访问会产生**跨地域流量费**并增加回源延迟，是部署前最易漏项的配置。
- **COS 侧配额（官方数据，非瓶颈）**：中国大陆公有云地域**单账号单地域默认上下行各 15 Gbit/s**（=源站 3 Mbps 的 5000 倍）、每桶**读写各 30000 QPS**、**单文件下载热点频控 1000 QPS**。**真实瓶颈始终在源站带宽与用户侧宽带，不在 COS。** 详见《前后端分离架构说明》§十一。
- **数据库只存元信息与对象键**，不存二进制内容。
- **成本约束**：对象存储与 CDN 按流量计费，须配置用量监控与费用告警；**COS 容量包仅抵扣存储容量，不含外网下行流量费**，须单独设定流量告警阈值。接入 CDN 后须配置防盗链（Referer 白名单），与签名 URL 的时效性叠加使用。

### 3.2 上传

- **类型白名单**（扩展名与 MIME 双重校验）：`.apk` `.exe` `.msi` `.dmg` `.zip` `.7z` `.rar` `.py` `.tar.gz` `.pdf` `.txt` `.md` `.json` `.yaml` `.ini` `.cfg` `.whl` `.AppImage` `.deb`
  > **2026-09-21 追加后三类**（A-18）。已复核安全性：`.whl` 为 zip 容器、`.deb` 为 ar 归档、`.AppImage` 为 ELF 可执行体，**均不会被浏览器内联解析执行**，与下方拒绝列表中的脚本类文件性质不同。MIME 对应：`.whl` → `application/zip`、`.deb` → `application/vnd.debian.binary-package`、`.AppImage` → `application/octet-stream`。
- **显式拒绝**：`.html` `.htm` `.svg` `.js` `.php` `.jsp` `.asp` `.sh` `.bat` `.cmd` —— 前四类可致存储型 XSS，后六类属服务端可执行类型，均存在明确安全风险。
- **单文件大小上限：200 MB**（已确认，覆盖绝大多数 APK 与脚本包）。超出即拒绝并给出明确提示。
- 上传由后端签发预签名凭证、前端直传对象存储；上传完成后回传对象键与 SHA-256，后端仅做格式校验（64 位小写十六进制）后落库——**方案 A（2026-09-21 已确认）**：不回拉对象重新计算校验值，避免 200 MB 回传流量；已知限制为校验值真实性依赖前端，管理员上传重要文件后应自行下载核对一次；不得以对象存储 ETag 冒充 SHA-256 对用户展示（详见 PRD 4.3）。
- 每工具版本数不设硬上限，但后台须展示占用总量。
- 上传接口必须要求登录态，并含 CSRF 防护、文件重命名。
- **不产生孤儿对象**：上传以"先落库占位、后完成对象写入"两步执行，或写入后立即登记；定时任务比对对象存储清单与数据库记录，清理无记录的残留对象。

### 3.3 下载

- **下载地址不得暴露对象存储的真实路径**。统一为 `/download/{file_id}` 形式，后端校验 `file_id` 有效性后返回 **302 重定向**至带时效的 **COS 预签名地址**（建议有效期 5 分钟；接入 CDN 后改为 CDN 签名地址，地址来源由配置项切换）。
- 响应头约定（由 COS／CDN 下发）：
  - `Content-Type: application/octet-stream`
  - `Content-Disposition: attachment; filename*=UTF-8''<encoded>`（解决中文文件名乱码）
  - `X-Content-Type-Options: nosniff`
  - `Content-Length`
- 下载计数在服务端重定向环节累加，不依赖 COS／CDN 日志。
- **文件缺失**（库中有记录、对象存储中无对象）返回 404，并在后台将该条目标记为"异常文件"，不做静默失败。
- 文件传输由 **COS（一期）／CDN（后续）** 承担，不占用应用服务器的带宽与进程；页面资源与文件下载互不争抢。

### 3.4 安全

- 对象存储桶设为**私有读写**，禁止公开读；一切访问经后端签发带时效的凭据。
- 防盗链：一期依赖 **COS 预签名 URL 的时效性**；接入 CDN 后追加 Referer 白名单（COS 亦支持，可视需要在一期开启）。响应带 `X-Content-Type-Options: nosniff` 并以附件形式下发，避免已上传文件被浏览器内联解析执行。
- 恶意文件：采取"**类型白名单 + 人工把关 + 声明性免责**"三项组合。个人站不承诺服务端病毒扫描，但必须在下载区公示："文件由作者本人打包上传，下载后请自行核对校验值"，并展示 SHA-256。

### 3.5 验收标准

1. 上传 150 MB 的 zip → 上传成功，专题页显示的大小与实际一致。
2. 下载所得文件的 SHA-256 与源文件一致。
3. 上传 250 MB 文件 → 被拒绝，提示明确，对象存储中无残留对象。
4. 上传 `.svg` 或 `.html` → 被拒绝。
5. 未经签名的对象存储地址直接访问 → 被拒绝；签名 URL 超过有效期后同样不可访问。
6. 下载中文名文件 → 下载后的文件名正确、无乱码。
7. 删除某版本文件后 → 前台该条目消失，对象存储中的对象与 CDN 缓存同步失效。
8. 尝试在专题页寻找预览入口 → 不存在；Web 工具以站外链接形式呈现。

# ADR-002：留言者联系方式（选填邮箱）

## 1. 定义

留言表单新增字段 `contact_email`：**选填、邮箱格式、仅管理员可见**，用于 BUG 跟进与修复结果告知。

定义中三个必须明确的界限：

1. **它是可选联系渠道，不是账号。** 邮箱不用于登录、不作为用户唯一标识、不做跨留言的去重与合并。
2. **它对访客不公开。** 包括提交者本人，也无法在公开留言区看到自己留下的邮箱——否则等于公开邮箱列表，会被批量采集。
3. **用途严格限定于本次留言的跟进。** 不得用于营销、订阅、二次触达无关事项。

## 2. 界面与文案

### 2.1 表单

- 字段标签：`邮箱（选填）`
- 字段下方常显说明：`仅管理员可见，用于向你反馈问题处理结果，不会公开显示。`
- 留空不拦截提交。
- 格式错误提示：`邮箱格式不正确，可留空。`
- 提交按钮下方或留言区底部，补一行站点级说明：`留言中的邮箱仅管理员可见，不会公开显示。`

### 2.2 文案一致性要求

上述措辞须在**三处保持一致**：前台表单、隐私政策页、PRD 正文。同一约束在不同位置出现不同说法，是后续争议与投诉的主要来源。

### 2.3 隐私政策须覆盖

| 项 | 内容 |
|---|---|
| 收集内容 | 邮箱地址（选填） |
| 收集目的 | 就本次留言内容进行问题跟进与处理结果告知 |
| 可见范围 | 仅站点管理员 |
| 保存期限 | 随对应留言一并删除 |
| 删除方式 | 由管理员删除留言即同步删除；亦可来信要求删除 |

## 3. 实现约束

### 3.1 数据模型

- `messages.contact_email`：字符串，允许 `NULL`，上限 254 字符（RFC 5321 邮件地址长度上限）。
- **不建唯一索引**——同一邮箱可对同一工具提交多条留言，用于追问与补充。
- 与留言同行存储，**不单独建立"订阅者"表**，避免数据模型向"用户体系"漂移。

### 3.2 校验

- 前端：`type="email"` 配合宽格式校验。
- 后端：格式校验 + 长度截断（≤254）。**后端是唯一可信校验点。**
- 不做 MX 记录等可达性校验——误杀正常邮箱，且个人站无此必要。
- **不发送验证邮件。** 一期不做邮箱验证，理由见 3.5。

### 3.3 可见性与访问控制（最关键的一条）

- **公开留言列表接口必须显式排除 `contact_email` 字段。** 采用后端序列化白名单输出，而非"前端不渲染"。仅靠前端隐藏，接口仍可被直接请求读取。
- 邮箱仅在后台管理端（需登录）可见，提供一键复制与 `mailto:` 跳转。
- 后台留言**列表页默认不展示邮箱**，仅在留言详情页展示——避免列表页在被截图或投屏时批量泄露。
- 数据导出：默认**不**导出邮箱字段；需管理员**显式勾选**方可导出（A-19 定稿），且导出文件表头带可见警示，**导出动作留审计记录**（操作人 + 时间 + 是否含邮箱）。

### 3.4 与其他能力的联动

- 后台支持按"有邮箱／无邮箱"筛选留言 —— 便于优先处理可联系的反馈。实现成本低、直接提升反馈闭环率，**建议纳入一期**。
- 若同一邮箱多次提交，可在留言详情显示历史提交条数，辅助识别重复问题（可延至二期）。

### 3.5 反滥用

- 选填邮箱 + 免登录留言确实便于垃圾提交。但关键在于：**一期不向邮箱发出任何邮件**，因此该字段不构成邮件轰炸入口。
- 这也正是"一期不发验证邮件、不发回复通知邮件"的核心理由。若二期引入邮件通知，必须同时引入发送频率限制与验证机制，届时单独评估。
- 邮箱字段本身仍受全站统一限流与关键词过滤约束（见 PRD 4.2）。

### 3.6 与"匿名留言"的关系

- 昵称与邮箱相互独立，四种组合均合法：真实昵称+邮箱、匿名昵称+邮箱、真实昵称+留空、匿名昵称+留空。
- **邮箱不得作为身份标识展示，也不得用于自动生成昵称。**
- 留言的公开标识始终只有昵称。

### 3.7 保存与删除

- 邮箱随留言一同删除：管理员删除留言时，该行（含邮箱）一并移除。
- 不设置独立的邮箱留存周期，避免"留言已删、邮箱仍在"的隐性留存。

### 3.8 验收标准

1. 前台提交留言，邮箱留空 → 提交成功。
2. 填写 `abc@` → 前端拦截并提示；绕过前端直接请求接口 → 后端拒绝。
3. **直接请求公开留言列表接口 → 返回体中不含 `contact_email` 字段。**
4. 后台留言详情页可见邮箱，可复制、可发起邮件。
5. 删除该留言 → 数据库对应行（含邮箱）被删除。
6. 前台表单、隐私政策页、PRD 三处文案一致，且均含"仅管理员可见"表述。
7. 导出数据时，未勾选则导出结果不含邮箱列。

# ADR-003：仓库形态（三仓库 + 本地工作区）

- **决策日期**：2026-09-21
- **决策人**：NecoOcean
- **状态**：已确认，**已升格为跨项目强制规范**
- **规范落点**：`docs/文档规范/仓库形态规范.md` v1.2

## 1. 决策

**采用「三仓库 + 一个不受版本控制的本地工作区」形态**：

| # | 仓库 | 内容 |
|---|---|---|
| ① | 后端 | `necoocean-tools-backend/` |
| ② | 前端 | `necoocean-tools-frontend/` |
| ③ | 文档 | 仓库根下 `docs/` 中间层内含 `doc/` + `design/` + `文档规范/`（本仓库实际路径 `docs/doc/`、`docs/design/`、`docs/文档规范/`；仓库根名为 `necoocean-vault`） |
| — | **本地工作区** | 根目录本身，**不纳入版本控制** |

**本 ADR 在其原始决策（原「仓库形态 = 前后端两个独立仓库」）基础上补入第三块**：文档仓库。原因见 §3。

## 2. 决策依据

| # | 理由 |
|---|---|
| 1 | **版本必须能独立演进**——后端打 tag 时前端与文档不应被迫跟随。git tag 是仓库级而非目录级的 |
| 2 | **部署单元本就分离**——后端产 jar → 服务器；前端产静态文件 → COS。发布、回滚、目标全不同 |
| 3 | **变更需要独立历史**——"查某接口哪次改的"与"查某参数哪次定的"是两个独立问题 |

**实证**：PRD 曾因参数持续回填，版本号从 v1.1 连推至 v1.7——"更新节奏不同的内容共用一个版本号"的代价，本仓库已有先例。

## 3. 为何是"三"而非"二"

原决策只写「前后端两个独立仓库」，但**文档事实上也需要独立版本控制**：

- 文档的变更节奏（决策变更时）与代码（每次实现）不同；
- 文档要能脱离代码单独分发给他人参考；
- 前端仓库尚未建立（**此为 2026-09-21 决策时状态；三仓库已于 2026-09-22 全部建成并推送**），而**文档仓库的缺失是当时实际风险**（根目录尚无 git，12 份文档无版本控制）。

## 4. 明确排除的方案

| 方案 | 排除理由 |
|---|---|
| **Monorepo**（根目录一个仓库装全部） | 收益前提是"模块间大量代码共享、需原子提交跨模块改动"。本项目前后端**零代码共享**，共享物仅一份 HTTP 契约且载体是文档不是代码。前提不成立 |
| **git submodule 挂根目录** | 价值是"锁定多仓库的特定版本组合"，本项目无此需求。代价：克隆后子目录为空、每次改动两次提交、漏更新指针即静默错版。**收益为零、成本为正** |

## 5. 与既有决策的关系

- 原「仓库形态 = 两个独立仓库」**不废止**，本 ADR 是其**扩展**（补第三块 + 明确工作区不做仓库）。
- 该扩展已**升格为跨项目规范**，适用于 NecoOcean 一切前后端分离的个人项目，不限于本仓库。
- 本仓库文档仓库（远端名 `necoocean-vault-docs`，本地目录名 `docs`）采用**布局 C**（`docs/文档规范/仓库形态规范.md` §3.1）：**仓库根 = 本地工作区中的 `docs/` 目录**，`doc/`、`design/`、`文档规范/` 三个子目录直接位于仓库根下。**2026-09-21 定稿**（当日历经布局 B → 布局 A → 布局 C 两次迁移，均完成全量路径引用校验与既有表述对齐）。新项目一律采用布局 C。
  > **布局 C 与布局 A 的唯一差别**：`docs/` 这一层在 A 中是仓库**内**目录（被 git 跟踪），在 C 中是**仓库根本身**（由本地目录名提供、不被 git 跟踪）。两种形态下仓库内文件路径完全相同。代价是布局 C 的 `.gitignore` 排除兄弟仓库须用 `../` 前缀（R3）。

## 6. 派生的强制约束（R1~R7）

完整条款见 `docs/文档规范/仓库形态规范.md` §四。要点：

1. **R1** 工作区根目录不得初始化 git
2. **R2** 三仓库平级，无嵌套（布局 C 的 `docs/` 即仓库根，不构成嵌套）
3. **R3** 文档仓库根目录须有 `.gitignore`，排除两个代码仓库；前缀与布局匹配（布局 C 用 `../`）
4. **R4** 三仓库命名统一 `necoocean-<项目>-{backend,frontend,docs}`
5. **R5** 接口契约唯一事实源是文档仓库，代码仓库内禁止第二份定义
6. **R6** 变更顺序不可逆：先改契约 → 后端实现 → 前端跟进
7. **R7** 每次发布须在文档仓库 CHANGELOG 记录三仓库的版本对应
