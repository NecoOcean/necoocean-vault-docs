# 设计与接口类文档规范

**版本**：v1.0
**生效日期**：2026-09-21
**适用范围**：系统设计文档、架构说明、技术选型（方案对比）、接口清单、配置项说明、数据字典
**上位规范**：`文档撰写通用规范.md`（本文不重复其内容，仅补充各类文档的专有结构）

---

## 一、设计与接口类文档族的关系

这类文档的共同命题是**回答"怎么搭、怎么调"**，而**不回答"要什么"**（后者属需求类文档）。

```
需求类（要什么）              设计类（怎么搭）                接口类（怎么调）
─────────────              ──────────────                ──────────────
PRD          ────定义────▶  架构说明（分层/部署/演进）  ────约束────▶  接口清单
  │                              │
  │                              ├──▶ 系统设计文档（模块/流程/数据流向）
  │                              ├──▶ 技术选型（组件为什么是它）
  │                              ├──▶ 配置项说明（N-5）
  └──────────────────────────────┴──▶ 数据字典（N-6）
```

**事实源归属（硬性，本仓库既定）**：

| 信息 | 事实源 | 冲突时的处置 |
|---|---|---|
| 需求 | **PRD** | 设计要求服从需求 |
| 架构决策（分层/部署/演进） | **前后端分离架构说明** | 其余文档引用，不复述 |
| 接口契约 | **附录C 接口清单** | 唯一事实源；后端实现服从 |
| 数据字段 | **PRD §8** | 系统设计文档引用 |
| 技术组件选型 | **技术选型文档** | 系统设计文档不重新论证 |

> **纪律**：设计类文档最易犯的错误是**重新论证已决策的事**。系统设计文档的元信息块应显式写"**本文不做什么**：不重新论证技术选型、不引入新决策"。

## 二、系统设计文档

### 2.1 定位

面向开发落地的**"怎么搭"总装文档**。它把散落在架构说明、接口清单、数据模型中的结论**综合导出为可施工的形态**，但**不新增决策**。

### 2.2 标准骨架

```
元信息块（含「文档定位」「本文不做什么」「关联文档+版本」）
一、结论先行           —— 一句话 + 单元数 + 模块数 + 设计主线 + 当前状态
二、系统上下文与部署视图 —— 上下文图、部署拓扑、请求路径分发表
三、分层架构           —— 各层职责、不职责
四、模块设计           —— 每个模块的职责、依赖、核心流程
五、数据设计           —— 实体关系图、级联删除、索引
六、关键流程           —— 时序图（上传、下载、鉴权）
```

### 2.3 撰写要点

**§一 结论先行**必须包含四件东西：

1. **一句话定性**（"这是一个单机同源部署的严格前后端分离应用"）
2. **量化组成**（"4 个部署单元"/"8 个业务模块"）
3. **设计主线表**：列出**贯穿全系统的约束**及其受影响模块。这是设计文档最有价值的部分——它解释了"为什么这些看似无关的模块都要改"。
4. **当前状态**（可否开工）

**§三 分层架构**

每层必须同时给出**职责**与**不职责**：

```markdown
| 层 | 职责 | 不职责 |
|---|---|---|
| 前端 Vue 3 SPA | 渲染、交互、体验层校验、轮询、直传 COS | **业务规则判定**（一律由后端裁定） |
```

> "不职责"列的价值：它是**防止职责蔓延**的契约。本项目"体验层校验"与"业务规则判定"的分离正依赖于此。

**§四 模块设计**（原"分层架构"）

给出模块清单表：模块名 / 职责 / 依赖 / 复杂度标注。**必须指出复杂度中心**：

> 例："**留言反馈与资源文件是复杂度中心**——前者承载邮箱可见性约束与审核分期机制，后者承载文件不经应用服务器的两阶段直传流程。"

**§五 数据设计**

- 实体关系图用 **Mermaid `erDiagram`**（见 `文档图表绘制规范.md` §五）
- **必须包含全部实体与全部字段**，不允许"为简洁省略字段"
- 汇总数字（实体数、外键数）必须与图**逐一对应**（本仓库曾出现正文写"4 条外键"而实际 5 条）
- 索引与唯一约束独立成表

**§六 关键流程**

时序图用 **Mermaid `sequenceDiagram`**。涉及多步校验的流程（如签名校验三步）应收进 `Note over`，避免图面过度展开。

## 三、架构说明

### 3.1 定位

架构决策的**唯一事实源**。它回答"系统怎么分层、怎么部署、怎么演进"，并**坦白架构的代价**。

### 3.2 标准骨架

```
元信息块
一、结论先行           —— 架构定性 + 必须先说清的风险 + 代价标注
二、设计前提与约束      —— 用户给定的前提逐条落实
三、整体架构           —— 架构图
四、目录结构与职责      —— 前端 / 后端分别
五、协作约定           —— 前后端分离时的接口协作、鉴权、CSRF
六、部署方案           —— nginx.conf、systemd
七、演进阶段 0~N       —— 每阶段的目标、触发条件、成本
八、分离架构的代价      —— SEO、首屏、复杂度
九、量化分析           —— 并发/带宽测算
```

### 3.3 撰写要点

| 要点 | 说明 |
|---|---|
| **§一 必须主动说出风险** | 如"你给的三个条件——前后端分离 + 静态资源由源站提供 + 3 Mbps——**三者叠加会与首屏 P75 ≤1.5s 直接冲突**"。风险不藏在后文 |
| **量化测算必须给出表格** | 并发人数 / 理论耗时 / 判定，三列 |
| **测算须标注未计入项** | 如"该测算未计入 RTT、TLS 握手与 JS 解析执行时间，**实际只会更差**" |
| **代价必须诚实标注** | 分离架构的固有权衡（SEO 需额外方案、首屏弱于 SSR）须列为独立章节 |
| **演进阶段必须给触发条件** | 不写"以后再说"，写"当 X 发生时进入阶段 N" |

**演进阶段表格式**：

```markdown
| 阶段 | 目标 | 触发条件 | 成本 |
|---|---|---|---|
| 0 | 单机同源部署 | 现在 | —— |
| 1 | 前端产物迁 COS 静态托管 | 源站带宽成为瓶颈 | 零 CDN 成本 |
```

> **注意**：需澄清"**COS 静态托管不是 CDN**"这类易混概念，否则会与用户"暂不引入 CDN"的要求冲突。

## 四、技术选型（方案对比）

### 4.1 定位

回答"**用什么实现，为什么是它而不是别的**"。**不改动任何需求口径**。

### 4.2 标准骨架

```
元信息块（含各版变更摘要块）
一、结论先行           —— 选型结论 + 依据的一句话概括
二、决策约束           —— 来自已定文档的硬边界（表格 + 来源列）
三、技术栈决策留痕      —— 作废内容（须标注）
四、组件选型与论证      —— 每个组件：候选对比 → 结论 → 依据
   4.1.x 专项论证      —— 争议大的组件展开定量论证
五、目录结构（如已作废须标注）
六、脚手架步骤         —— 可执行的落地步骤
```

### 4.3 撰写要点

**§二 决策约束**是本文的独特价值——它把"选型不是自由发挥"变成可核验的表格：

```markdown
| # | 约束 | 取值 | 来源 |
|---|---|---|---|
| 5 | **带宽上限** | **3 Mbps（≈375 KB/s）** —— **本方案最紧约束** | 实购规格 |
| 7 | 接口规模 | 48 个 | 附录C §1 / §7 |
```

**"来源"列必填**——它使约束可追溯，防止选型讨论脱离既定前提。

**§四 组件论证**的写法（以数据库选型为例）：

1. **负载测算**：给出具体数字（峰值读 0.14 QPS、平均写 0.00006 TPS、10 年数据 53 MB）
2. **候选对比**：逐项列优劣，**不做未加限定的单一推荐**
3. **结论 + 依据**：明确结论**依据什么、不依据什么**

> **范例（本仓库实际采用的高质量写法）**：
> "**结论**：维持 MySQL 8。**依据是"迁移成本高于收益"，不是"SQLite 扛不住"。** —— SQLite 在纯性能维度完全够用，距其瓶颈 3~4 个数量级。"
>
> 这种写法把"结论"与"常见的错误归因"分开，避免后续被误读为"性能不足"。

**代价与收益必须两侧都写**：收益侧（省 100 MB 内存）、成本侧（7 类改造点，标注每项难度），并指出**哪几项属于"以后难改"**。

**§六 脚手架步骤**：编号步骤 + 每步的产物 + 验收方式。**第一步应当是日志骨架**（符合 NecoOcean 的日志能力审查永久约定）。

### 4.4 作废内容的处理

技术选型文档因决策反转频繁，**作废内容最多**。规则：

- 就地作废：`~~原文~~` + `**⚠️ 已作废（v0.3）**：原因 + 改按什么实施`
- 整节作废：章首加醒目引用块
  ```markdown
  > ⚠️ **本节与 §五 已作废**（2026-09-21 14:55，架构改为严格前后端分离）。
  > 以下内容仅作决策留痕，**请勿按此实施**。当前有效内容见《前后端分离架构说明》v1.2。
  ```
- **长期建议**：整篇作废的大段内容迁入 `docs/doc/_archive/`

## 五、接口清单

### 5.1 定位

接口的**唯一事实源**。PRD 描述"要什么"，接口清单描述"怎么调"。

> **冲突规则（须写入元信息块）**：「二者冲突时**以 PRD 为准**，但须同步修订本附录」。这条规则的存在使本文件可以在需求变更后安全地滞后一小段时间。

### 5.2 标准骨架

```
元信息块（文档版本 / 文档状态 / 本版改动 / 关联文档+版本 / 文档定位）
使用说明           —— 标记含义、分期落地说明、与 PRD 待补项的对应关系
一、统一约定（Contract）
   1.1 路由规范
   1.2 鉴权方案
   1.3 统一响应结构
   1.4 分页约定
   1.5 错误码规范
   1.6 限流约定
   1.7 缓存约定
   1.8 前后端分离协作约定
二～三、接口条目（按模块分组）
四、错误码表
五、数据结构约定
六、状态码与 HTTP 映射
```

### 5.3 接口条目的写法

每条接口必须包含六项：

```markdown
### C-07　提交留言

| 项 | 内容 |
|---|---|
| 方法 | `POST` |
| 路径 | `/api/v1/public/tools/{slug}/messages` |
| 鉴权 | 无需（公开接口，豁免 CSRF） |
| 限流 | 60 秒 5 条（按 IP 哈希） |

**请求参数**
| 参数 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| nickname | string | 否 | ≤20 字 | 留空显示"匿名访客" |
| contact_email | string | 否 | ≤254 字，邮箱格式 | 🔒 仅管理员可见 |
| category | string | 是 | 枚举 4 类 | 使用体验/功能建议/BUG报错/问题咨询 |
| content | string | 是 | ≤1000 字 | —— |
| repro_steps | string | BUG 类必填 | ≤2000 字 | 复现步骤 |

**响应**
| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint | 留言 ID |
| audit_status | tinyint | 1=待审核 2=已通过 |

**错误码**：`42201` 邮箱格式不正确 / `42900` 触发限流

> 🔒 **输出白名单**：响应不得包含 `contact_email`。
```

### 5.4 撰写要点

| 要点 | 说明 |
|---|---|
| **编号 `C-xx` 连续唯一** | 一经分配不复用 |
| **每条接口必须有方法 + 路径 + 鉴权 + 限流** | 四项缺一不可 |
| **敏感接口加 🔒** | 并显式写出**输出白名单要求** |
| **错误码集中成表** | 编号 / HTTP 状态 / 文案 / 触发场景 |
| **响应结构统一信封** | `{code, message, data}`，`code` 面向代码、`message` 面向用户 |
| **例外必须说明** | 如 `/download/{file_id}` 不带 `/api` 前缀且返回 302 而非 JSON，须写明理由 |
| **分期接口须标注** | 用 🔀 标记，并说明一期行为 / 二期行为 / 切换成本 |

**分期落地表格式（本仓库范例）**：

```markdown
| 层 | 一期行为 | 二期行为 | 切换成本 |
|---|---|---|---|
| 数据库 | `audit_status` 默认写 2 | 默认值改为 1 | 改一个默认值 |
| 提交接口 C-07 | 按当前策略自动置 | 同左（逻辑不变） | 无需改动 |
| 审核接口 C-45~C-47 | **实现**，但无待审数据 | 投入使用 | 无需改动 |
```

**并须写明"底线"**：

> ⚠️ **一期不得省略 `audit_status` 字段**。若为"简化"延到二期，则二期需改表 + 回填 + 改查询 + 改返回 + 新增接口 + 回归全部用例。**这是本方案唯一必须守住的底线。**

### 5.5 使用说明章

接口清单体量最大，**必须在正文最前给"使用说明"**，包含：

1. 本草案当前可否评审（契约层是否依赖未定参数）
2. **标记含义表**（✅ ⚠️ 🔒 🆕 🔀）
3. 分期落地说明（最重要的一节）
4. 与 PRD 待补项的对应关系（本清单解决了 PRD 的哪几项缺口，哪几项须回填 PRD）

## 六、配置项说明（N-5，待建）

### 6.1 当前状态

`nginx.conf`、`application.yml`、`.env` 等配置散落在架构说明与系统设计文档的代码块中，**无集中说明**。风险：改配置时须翻多份文档，易漏。

### 6.2 建议骨架

```
一、配置文件清单        —— 文件 / 位置 / 用途 / 是否入版本控制
二、运行环境变量        —— 变量名 / 必填 / 默认 / 说明 / 敏感标注
三、Nginx 配置说明      —— 逐段说明关键指令及其理由
四、应用配置说明        —— 数据库、COS、日志、限流
五、构建期配置          —— 环境变量、构建产物路径
六、敏感信息管理        —— 哪些不入库、如何注入
```

### 6.3 撰写要点

- **每条配置必须说明"为什么是这个值"**，而非只列值。如 `server.forward-headers-strategy=native` 须注明"否则限流会误伤全部访客"。
- 敏感项加 🔒 并说明注入方式，禁止在文档中写真实密钥。
- 配置项与代码中的默认值必须一致，不一致须显式说明原因。

## 七、数据字典（N-6，待建）

### 7.1 当前状态

数据模型在 `PRD §8`，但字段语义、枚举取值、索引说明**混合在需求文档中**。当表数量增长后，需求文档会变得难以维护。

### 7.2 建议骨架

```
一、实体总览            —— 实体清单 + 关系摘要（含实体数、外键数）
二、实体关系图           —— Mermaid erDiagram（全字段）
三、逐实体字段定义        —— 按 §8 的字段表格式
四、枚举值字典           —— 每个枚举的全部取值 + 含义 + 使用位置
五、索引与约束           —— 索引名 / 字段 / 类型 / 用途
六、变更历史            —— 与 Flyway 迁移脚本编号对应
```

### 7.3 与 PRD 的关系

- **事实源仍是 PRD §8**；数据字典是其**展开形态**，不做口径改动。
- 数据字典建成后，PRD §8 可精简为"字段定义见 `docs/doc/02-设计与实现/数据字典.md`（N-6，待建）"（N-6，待建），但**变更须同时记录在 PRD 修订记录中**。
- 枚举值字典是本文档最有价值的部分——本仓库曾出现"留言状态 4 种 vs 2 种"的口径冲突，根因即缺少集中枚举表。
