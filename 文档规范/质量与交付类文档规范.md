# 质量与交付类文档规范

**版本**：v1.0
**生效日期**：2026-09-21
**适用范围**：测试计划与用例集、部署运维手册、CHANGELOG、项目 README、日志能力评估报告
**上位规范**：`文档撰写通用规范.md`（本文不重复其内容，仅补充各类文档的专有结构）

---

## 零、这类文档的共同特征

质量与交付类文档与需求/设计类有一个根本差别：**它们描述"动作"而非"状态"**。

| 对比项 | 需求/设计类 | 质量与交付类 |
|---|---|---|
| 读者 | 决策人、设计者 | 执行者（可能是不熟悉项目的自己） |
| 时态 | 陈述"是什么" | 祈使"怎么做" |
| 成功判据 | 口径一致、无矛盾 | **照着做能复现** |
| 常见失手 | 表述模糊 | 跳步、隐含前提、无回滚方案 |

**最高判据**：**一份部署手册，若另一个没参与过项目的人照做能成功部署，才算合格。**

> **本仓库现状**：这五类文档**全部缺失**（详 `README.md` §3.2）。其中**测试用例集**与**部署运维手册**是最紧缺口。

## 二、测试计划与用例集（N-1）

### 2.1 定位

《验收用例集》（N-12，独立文档）是**验收视角**（"达到什么状态算满足"）；测试用例集是**执行视角**（"我要点哪里、看什么、记什么"）。二者不可互相替代，且**成对使用**——验收用例的"关联需求"列应指向 PRD 章节，测试用例的"关联需求"列可指向验收用例编号 `B-xx`。

### 2.2 标准骨架

```
一、测试范围与策略
   1.1 测试对象与版本
   1.2 测试类型（功能/接口/性能/安全/兼容）
   1.3 环境要求
   1.4 准入准出条件
二、测试用例
   2.1 功能用例（按模块）
   2.2 接口用例
   2.3 性能用例
   2.4 安全用例
   2.5 兼容性用例
三、缺陷管理
   3.1 缺陷分级
   3.2 状态流转
四、测试报告模板
```

### 2.3 用例的标准格式（强制六列）

| 列 | 说明 |
|---|---|
| **用例编号** | `TC-{模块}-{序号}`，如 `TC-MSG-007`。**连续唯一，不复用** |
| **前置条件** | 执行前必须满足的状态。**不允许写"无"**——若真无前置，写"已登录管理员账号"或"站点处于初始状态" |
| **操作步骤** | 编号步骤，**逐步可执行**，不合并 |
| **预期结果** | **可观测**的具体结果（页面元素 / 响应码 / 数据库状态） |
| **关联需求** | 指向 PRD 章节或 `B-xx` 验收项 |
| **优先级** | P0（阻断）/ P1（主要）/ P2（次要） |

**范例**：

```markdown
| 项 | 内容 |
|---|---|
| **用例编号** | TC-MSG-007 |
| **前置条件** | 站点已开启留言功能；工具 `demo-tool` 存在 |
| **操作步骤** | ① 打开 `/demo-tool` 专题页<br>② 分类选择"BUG报错"<br>③ **不填**复现步骤<br>④ 点击提交 |
| **预期结果** | ① 步骤③ 页面就地提示"BUG 类留言须填写复现步骤"<br>② 步骤④ 请求未发出（前端拦截）<br>③ 若绕过前端直接 POST，后端返回 `42202`<br>④ 数据库 `messages` 表**无新增记录** |
| **关联需求** | PRD §4.2 / B-12 |
| **优先级** | P0 |
```

### 2.4 撰写纪律

| 纪律 | 说明 |
|---|---|
| **预期结果必须含"反向验证"** | 不只看"成功了"，还要看"不该发生的没发生"（如"数据库无新增记录"） |
| **前端校验与后端校验分别验证** | 这是本仓库的安全约定（前端校验仅为体验，后端才是裁定） |
| **限流类用例必须说明规避方式** | 如"连续提交 6 次后，第 6 次返回 429；测试期间需注意 IP 桶污染" |
| **性能用例必须写明口径** | 直接引用《待确认参数台账》的并发口径定义（如 `A-16`），不得自创 |
| **禁止**"功能完整无 BUG"式判据 | 每条用例必须可判定通过/失败 |

### 2.5 缺陷分级标准（建议）

| 级别 | 定义 | 处置时限 |
|---|---|---|
| **致命** | 数据丢失、安全漏洞、服务不可用 | 立即阻断发布 |
| **严重** | 主要功能不可用，无绕过方案 | 发布前必须修复 |
| **一般** | 功能可用但有错误，有绕过方案 | 可延至下一版 |
| **轻微** | 文案、样式、体验问题 | 可延至下一版 |

## 三、部署与运维手册（N-2）

### 3.1 定位

**唯一能让部署可复现的载体**。本仓库当前部署知识散落在架构说明 §七、系统设计文档 §2.2 与对话记录中，**不可复现**。

### 3.2 标准骨架

```
一、环境要求            —— 硬件规格、操作系统、依赖软件及版本
二、首次部署
   2.1 服务器初始化      —— 用户、目录、时区、防火墙
   2.2 依赖安装          —— JDK、Nginx、MySQL 及版本
   2.3 数据库初始化       —— 建库、账号、执行迁移脚本
   2.4 应用部署          —— jar 上传、systemd 单元、启动
   2.5 前端部署          —— 本地构建、产物上传、Nginx 指向
   2.6 Nginx 配置        —— 完整配置 + 逐段说明
   2.7 HTTPS 证书        —— 申请、配置、自动续期
   2.8 部署后验证        —— 逐项检查清单
三、配置项
   3.1 环境变量
   3.2 数据库连接
   3.3 COS 配置
四、日常运维
   4.1 启停与重启
   4.2 日志查看
   4.3 数据库备份与恢复
   4.4 磁盘与流量监控
   4.5 证书续期
五、版本发布流程        —— 灰度/回滚
六、故障处理
   6.1 常见故障与处置
   6.2 回滚方案
七、应急联系
```

### 3.3 撰写要点

**① 所有命令必须可直接复制执行**

```bash
# ✅ 正确：含路径、含参数、无占位符歧义
sudo systemctl restart necoocean-tools

# ❌ 错误：读者需自行推断
重启应用服务
```

若需占位符，统一用 `<尖括号>` 标注并说明取值来源。

**② 每步之后必须有"验证方式"**

```markdown
**步骤 2.4.3　启动应用**

```bash
sudo systemctl start necoocean-tools
```

**验证**：`systemctl status necoocean-tools` 显示 `active (running)`；
`curl -s http://127.0.0.1:8080/api/v1/public/tools | head -c 100` 返回 JSON 信封。
```

**③ 部署后验证清单必须独立成节**

这是手册中最有价值的部分——它把"部署成功"从主观判断变成逐项核验：

```markdown
### 2.8 部署后验证

- [ ] `curl -I https://<域名>/` 返回 200，`Content-Type: text/html`
- [ ] `curl -s https://<域名>/api/v1/public/tools` 返回 `{"code":0,...}`
- [ ] **jar 内不含任何 `.html`**：`unzip -l app.jar | grep -c '\.html$'` 结果为 0
- [ ] **除 `/download/*` 的 302 外，所有响应 Content-Type 均为 JSON**
- [ ] **真实 IP 透传生效**：`X-Forwarded-For` 有值，非 `127.0.0.1`
- [ ] 封面图直连 COS 可访问，源站未被占用
- [ ] `mysqldump` 定时任务已就位
- [ ] 磁盘与流量告警已配置
```

> **注意**：验证清单中的前四项直接来自本仓库既定的验收口径（"jar 内不得含 .html""除 302 外响应必为 JSON"）。**手册必须把这些口径承接进来**，否则它们只存在于架构文档中、无人验证。

**④ 回滚方案必须与部署方案同时给出**

| 发布方式 | 回滚动作 |
|---|---|
| 后端 jar 替换 | 保留上一版 jar，`systemctl stop` → 替换 → `start` |
| 前端产物替换 | 保留上一版 `dist` 目录，直接换回 |
| 数据库迁移 | **必须评估是否可逆**；不可逆迁移须先备份并写明恢复步骤 |

**⑤ 危险操作必须加醒目警告**

```markdown
> ⚠️ **此操作会清空 `messages` 表**。执行前必须确认已备份：
> `mysqldump -u root -p necoocean > backup_$(date +%Y%m%d).sql`
```

**⑥ 隐含前提必须显式化**

本仓库的已知隐含前提（须写入手册）：

- Nginx 反代后 **必须正确取 `X-Forwarded-For` 首段**，否则限流会误伤全部访客；取不到时**降级为不限流**，不得归入同一桶
- **COS 建桶地域必须与轻量服务器同在上海**，否则产生跨地域流量费
- 前端**必须在本地构建**后上传产物，服务器不安装 Node
- 一期**不接 CDN**，但 COS 签名地址机制须保留

## 四、变更记录 CHANGELOG（N-3）

### 4.1 定位

各文档各自维护的修订记录是**文档视角**（"这份文档改了什么"）。CHANGELOG 是**项目视角**（"这个项目发生了什么"）。二者不可互相替代。

### 4.2 存放位置与格式

存放于仓库根目录 `CHANGELOG.md`，遵循 [Keep a Changelog](https://keepachangelog.com/) 的语义化版本约定：

```markdown
# 变更记录

本文件记录 `necoocean-vault` 的全部重要变更。
格式遵循 Keep a Changelog，版本号遵循语义化版本。

## [Unreleased]

### Added
- 文档规范目录（通用规范 + 3 份分类规范 + 图表规范 + 绘图 Prompt）

### Changed
- 全部文档图表重绘：19 张不合规图修正为合规

### Fixed
- `系统设计文档` §5.1 外键数由 4 条更正为 **5 条**
- `前后端分离架构说明` §三 「会话/登录态」层级归属修正

## [0.1.0] - 2026-09-21

### Added
- PRD v1.7、一期功能清单 v1.7、附录C v0.8、系统设计文档 v1.0
- 架构说明 v1.2、技术选型 v0.5、ADR-001/002
```

### 4.3 变更类型（六类，固定）

| 类型 | 含义 |
|---|---|
| `Added` | 新增功能或文档 |
| `Changed` | 已有内容的变更 |
| `Deprecated` | 即将废弃（本文档类项目中少用） |
| `Removed` | 删除 |
| `Fixed` | 错误修正 |
| `Security` | 安全相关修正 |

### 4.4 撰写纪律

| 纪律 | 说明 |
|---|---|
| **面向"用户可感知的变化"，而非逐次提交** | 不记录"修正了错别字"这类 |
| **`Fixed` 必须写明"从什么改成什么"** | 如"外键数由 4 条更正为 5 条"，使错误可追溯 |
| **日期用 `YYYY-MM-DD`** | 遵循 Keep a Changelog |
| **未发布内容留在 `[Unreleased]`** | 发布时移入版本号节 |
| **与文档修订记录的分工**：CHANGELOG 记"跨文档的重要变化"，文档修订记录记"本文档的每一处改动" |

## 六、日志能力评估报告（N-10）

### 6.1 定位

依据 NecoOcean 的**永久生效约定**：每开始新项目或接手既有代码库时，**第一件事**是审查日志能力，先于任何功能开发。

### 6.2 固定三块结构（强制）

```
(a) 已具备项  —— 逐条给出证据（文件路径 + 行号或配置项）
(b) 缺失项    —— 标注严重程度
(c) 改进建议  —— 按优先级排序，可执行、可验收
```

### 6.3 审查四维度（缺一不可）

| 维度 | 审查问题 |
|---|---|
| **1. 运行时日志的自动生成机制** | 是否有统一 logger 入口？关键路径（启动、请求入口、外部调用、后台任务、异常分支）是否都有埋点？埋点是散落的 `print`/`console.log` 还是收口到 logger？日志上下文是否带 request_id / trace_id / 用户标识？ |
| **2. 持久化存储策略** | 输出目标（stdout / 文件 / 系统日志 / 远程采集）？存储位置与目录约定？格式（纯文本 / JSON Lines）？**轮转与保留周期**？磁盘占用上限与超限行为？敏感字段是否脱敏？ |
| **3. 日志级别划分的合理性与规范性** | 是否定义并统一使用 DEBUG/INFO/WARN/ERROR/FATAL？各级别使用准则是否明确（哪些算 ERROR、哪些只是 WARN）？级别可否通过配置调整而不改代码？是否存在级别误用？生产默认级别是否合理？ |
| **4. 异常与错误的捕获、堆栈记录与上报** | 是否有全局兜底（顶层异常处理器 / 信号处理 / 未捕获 Promise 拒绝 / 崩溃钩子）？是否**完整记录堆栈**而非只记 message？错误对象是否保留 cause / 嵌套调用链？是否上报或落盘错误日志？是否有聚合去重与告警阈值？异步/并发场景下堆栈是否被吞掉？ |

### 6.4 判定纪律（最关键）

> **没有实际代码或配置证据的项一律归入"缺失"或"待确认"，绝不因"通常都会有"而默认为已具备。审查结论必须能追溯到具体文件。**

### 6.5 建议的评估表格式

```markdown
| 维度 | 项 | 判定 | 证据 |
|---|---|---|---|
| 1 | 统一 logger 入口 | ❌ 缺失 | 无 `logger` 配置类 |
| 2 | 日志轮转 | ⚠️ 待确认 | `application.yml` 未见 `logging.logback.rollingpolicy` |
| 3 | 级别准则 | ❌ 缺失 | 无级别使用规范文档 |
| 4 | 全局异常兜底 | ❌ 缺失 | 无 `@RestControllerAdvice` |
```

**改进建议必须可验收**：

| 层次 | 表述 |
|---|---|
| ❌ | "完善日志" |
| ✅ | "新增 `logback-spring.xml`，配置 `SizeAndTimeBasedRollingPolicy`：单文件 100 MB、保留 30 天、总量上限 3 GB；`logging.level.root=INFO` 生产默认" |
